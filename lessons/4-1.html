1. What Firebase Auth actually does

▶ YouTube reference — the video for this lesson

You hand Firebase an email and password; it verifies credentials, issues the user an identity (uid), and keeps a session alive across reloads. Your code never sees or stores passwords — that entire risk class (hashing, resets, breaches) belongs to Firebase. Skillzify uses Email/Password only, with one account shared by web and Android: project skillzify-1d0f2.

2. Auth state is a stream, not a snapshot

▶ YouTube reference — the video for this lesson

▸ Code example — see the Code section below.

The classic beginner bug is checking "current user" once on page load — at that moment Firebase may still be restoring the session and reports null for a signed-in user. onAuthStateChanged fires when the state is known and again on every sign-in/out. Skillzify's auth.js (compat SDK 11.3.1) builds the whole login flow around this listener.

3. The public API key paradox

▶ YouTube reference — the video for this lesson

Skillzify's web config — including its API key — sits in plain sight in auth.js. This is by design: the key identifies the project, not a secret credential. Real security comes from Firestore security rules (Lesson 4.4) and the list of authorised domains in the Firebase console. A leaked "key" that only identifies a locked-down project grants nothing.

UX detail that mattersAuth errors should be human: "wrong password" beats Firebase's raw error codes. Map codes to friendly messages in auth.js, and never reveal whether an email exists on password-reset flows.

3 · Code

firebase.auth().onAuthStateChanged((user) => {
  if (user) { loadProgress(user.uid); showApp(); }
  else { showLogin(); }
});

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

Why is checking firebase.auth().currentUser once on page load unreliable?

Session restoration is asynchronous; currentUser can be null at load even for a signed-in user. onAuthStateChanged reports the state once it is actually known.

If the Firebase web API key is public, what actually secures the data?

Firestore security rules (per-user access control) plus authorised domains in the console. The key identifies the project; rules enforce access.

6 · Interview

A user pastes your Firebase config from view-source and says your app is hacked. Respond.

The web config is public by design — it identifies the project. Security is enforced by Firestore rules and authorised domains; demonstrate a denied cross-user read to prove it.

How does your app know a user is signed in on page load?

It doesn't guess: onAuthStateChanged fires after session restoration with the user or null, and the UI renders from that event.
