Goal — by the end of this lessonBy the end you can design a failover chain across models and keys, explain Skillzify's rotation and caps as one system, and estimate the cost of an AI feature before building it.

1. Everything fails; design the order of falling back

▶ YouTube reference — the video for this lesson

Skillzify's server tries a primary Gemini model, and on failure (quota, overload, error) walks a failover list across 6 models — 2.5-flash family, flash-lite variants and newer releases. The principle: a slightly weaker model's answer beats an error page. Failover order is a product decision — order by (quality × availability), and log which rung served each request, or you'll never know your real reliability.

2. Key rotation: quota as a pool

▶ YouTube reference — the video for this lesson

Free-tier quotas attach per key/project. Skillzify holds several keys (GEMINI_API_KEYS) and rotates, multiplying headroom (verified capacity ~1,080 calls/day across keys). Rotation pairs with Module 3.4's per-user caps: caps stop one user draining the pool; rotation sizes the pool.

3. Cost estimation: arithmetic before architecture

▶ YouTube reference — the video for this lesson

▸ Code example — see the Code section below.

Run this napkin math for every AI feature before building it. It tells you your cap values, whether streaming is worth it, and when a feature needs a paid tier. Also design for model churn: Skillzify's primary model auto-routes to a successor on a set date — pinning your product to one model name forever is a scheduled outage.

Retry disciplineRetry transient failures (5xx, timeouts) with a small backoff, once or twice. Never retry validation errors or refusals — you'll pay to fail repeatedly. And every retry counts against caps and cost.

Why is a weaker model's answer usually better than an error?

The feature's value is the answer; a slightly lower-quality successful response preserves the user experience, and you can log and tune quality separately from availability.

Caps and key rotation solve different problems — which is which?

Caps bound demand per user (cost/abuse control). Rotation expands supply (pooled quota across keys). You need both: pooled supply is still finite.

7 · Interview ▾

Your AI feature must stay up on a free tier. Architecture?

Per-user caps and rate limits on my server, a pool of API keys with rotation, model failover ordered by quality/availability, logged fallback rates, and graceful degradation messaging when everything is down.

How do you estimate an LLM feature's running cost?

Users × calls per user × average tokens per call × price per token — computed per day/month before building, then validated against real usage logs.
