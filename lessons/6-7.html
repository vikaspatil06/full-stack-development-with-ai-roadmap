Debugging in the Browser

DevTools is the debugger — breakpoints, scopes, and the network tab

2 · Read

Goal — by the end of this lessonBy the end you can set breakpoints and conditional breakpoints, inspect scope and the call stack, debug a failing fetch in the Network tab, and reproduce a bug before fixing it.

1. Breakpoints beat console.log

▶ YouTube reference — the video for this lesson

Scattering console.log calls tells you what happened at points you guessed in advance. A breakpoint stops execution exactly where you choose, and while paused you can inspect every variable in scope, hover expressions, and step line by line. Conditional breakpoints go further: pause only when the lesson ID equals the broken one, or when the counter passes one hundred — invaluable when a bug appears once in a thousand iterations. The debugger statement in code does the same thing from the source: when DevTools is open, execution pauses there.

2. The call stack tells you how you got here

▶ YouTube reference — the video for this lesson

When paused, the call stack shows the chain of function calls that led to this line. That is usually where the bug lives — not in the line that threw, but in the caller that passed the wrong value three frames up. The Scope panel shows local variables, closures and globals side by side, so you can see which value is wrong and where it came from. Watch expressions pin the values you care about across steps, so you notice the moment one goes wrong.

3. The Network tab debugs the backend you cannot see

▶ YouTube reference — the video for this lesson

Half of frontend bugs are not in the frontend. The Network tab shows every request: its URL, status, headers, payload and response, with timing. A tutor call that returns nothing is diagnosed here in seconds — wrong endpoint, missing auth header, a 500 with an error body, a CORS rejection. Pair it with the Console for errors and the Application tab for localStorage and IndexedDB, and most Skillzify bugs become visible before you touch any code.

▸ Code example — see the Code section below.

Rule of the craft: reproduce first, fix second. A fix for a bug you cannot reproduce is a guess you cannot verify.

3 · Code

// The three debugging moves, in order:
// 1. Reproduce it reliably — same steps, same result, every time.
// 2. Pause it: set a breakpoint, or add this line where it breaks:
debugger; // pauses here when DevTools is open
// 3. Inspect: Scope panel for values, Call Stack for how you got here,
//    Network tab for what the server actually returned.

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

Why is a conditional breakpoint better than a plain one in a loop that runs a thousand times?

It pauses only when the condition matches — the one broken iteration — instead of forcing you to step through 999 correct ones.

A fetch returns nothing useful. Which DevTools tab diagnoses it first, and what do you look for?

The Network tab: the request's status, payload and response body show whether the endpoint, headers or server reply is wrong.

6 · Interview

Walk me through debugging a bug you cannot reproduce on your machine.

Reproduce with the user's exact steps and data, add logging at the boundaries, check environment differences like cached files or auth state, and bisect recent changes.

When do you use console.log anyway, despite having a debugger?

For async flows and timing issues where pausing changes the behaviour, and for quick traces across many events where breakpoints would be too slow.
