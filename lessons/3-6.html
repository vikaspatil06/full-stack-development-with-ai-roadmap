Goal — by the end of this lessonBy the end you can explain the difference between a rate limit and a daily cap, why API keys must never reach the browser, and how Skillzify layers all three defences.

1. Two different problems, two different tools

▶ YouTube reference — the video for this lesson

  • Rate limit — "30 requests per minute per IP" in Skillzify. Stops bursts: scripts, loops, abuse spikes. Window: seconds/minutes.
  • Daily cap — 50 AI calls/day signed-in, 10/day anonymous. Stops slow-drain cost abuse and keeps a free tier affordable. Window: a day, per user.

A rate limit without a cap still lets a patient abuser spend your whole budget by midnight. A cap without a rate limit lets one script burn a user's day in four seconds. You need both.

2. Secrets live on the server. Full stop.

▶ YouTube reference — the video for this lesson

Anything shipped to a browser is public — view-source is not hacking. Skillzify's browser code calls /api/*; the server attaches the Gemini key, which lives only in Render environment variables (loaded locally from a gitignored .env via dotenv). Key rotation — several keys, server cycles through them — spreads quota so one key's limit doesn't take the product down.

▸ Code example — see the Code section below.

3. Know the honest limits

▶ YouTube reference — the video for this lesson

Skillzify's own notes admit the gaps: caps held in server memory reset when the free-tier service restarts, and full persistence needs Firestore-backed counters (firebase-admin is already a dependency for exactly this). Naming your system's real limits — in the design, not after an incident — is senior-level honesty.

The pattern to reuse everywhereValidate → rate limit → cap → spend. In that order, cheapest check first, expensive resource last.

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

Rate limit vs daily cap — what different abuse does each stop?

Rate limits stop bursts and scripts in short windows; daily caps stop slow, sustained cost drain across a day per user.

A teammate suggests putting the Gemini key in the frontend 'just for the demo'. Your answer?

No — anything in browser code is public. The key goes in server env vars; the browser calls your API, the server calls Gemini.

6 · Interview

Your free AI feature is being abused. Walk me through your defences in order.

Server-side validation and size limits first, then per-IP rate limits for bursts, then per-user daily caps for cost, keys only in env vars with rotation, and monitoring on spend.

Why do caps belong on the server, not the client?

Client state is user-controlled — clearable, editable, scriptable. Server (ideally database-backed) counters are the only ones that bind.
