SQL Deep — Indexes, Transactions & Window Functions

Make queries fast and writes safe

1. Indexes: the sorted shortcut

▶ YouTube reference — the video for this lesson

Without an index, finding rows means scanning the whole table — fine for a hundred rows, fatal for ten million. A B-tree index keeps a sorted copy of one or more columns in a balanced tree, so the database jumps straight to matching rows in logarithmic time instead of reading everything. The cost is paid on writes: every insert and update must also update every index on the table, and indexes consume disk. Index the columns you filter and join on; do not index everything.

Skillzify stores its data in Firestore, which builds single-field indexes automatically but has no joins and no multi-document transactions with the same guarantees as SQL. Knowing SQL indexes explains what Firestore is doing for you under the hood — and why a composite query there needs a composite index created by hand.

2. EXPLAIN: read the plan before you guess

▶ YouTube reference — the video for this lesson

EXPLAIN shows the plan the database chose: which index it used, whether it scanned the whole table, and how many rows it expects to touch. A sequential scan on a large table where an index exists usually means the index does not match the query — wrong column order, a function wrapped around the column, or statistics the planner does not trust. The habit that separates good SQL developers is simple: never optimise by guessing; run EXPLAIN, find the expensive step, and fix that one thing.

3. Transactions and ACID

▶ YouTube reference — the video for this lesson

A transaction groups several writes so they succeed or fail together. ACID names the guarantees: Atomicity (all or nothing), Consistency (constraints always hold), Isolation (concurrent transactions do not see each other's half-finished work), and Durability (committed data survives a crash). Isolation levels trade safety for speed: read committed prevents dirty reads, repeatable read also prevents rows changing mid-transaction, and serializable makes concurrent transactions behave as if they ran one at a time. Awarding XP and updating a leaderboard in one transaction is exactly the shape of problem ACID solves.

4. Window functions: rankings without self-joins

▶ YouTube reference — the video for this lesson

Window functions compute over a set of rows related to the current row, without collapsing them into one. ROW_NUMBER() numbers rows within each group, RANK() gives ties the same rank and skips the next numbers, and DENSE_RANK() gives ties the same rank without skipping. The classic use is top-N per group: rank each learner's attempts per lesson, then keep rank 1. Before window functions this needed a self-join; now it is one readable query.

SELECT lesson_id, user_id, score,
       ROW_NUMBER() OVER (
         PARTITION BY lesson_id ORDER BY score DESC
       ) AS rn
FROM attempts;

-- Top attempt per lesson: wrap the above and filter rn = 1.
-- Speed it up with a matching index:
CREATE INDEX idx_attempts_lesson_score
  ON attempts (lesson_id, score DESC);

Why does adding an index slow down writes?

Every insert, update and delete must also maintain each index on the table, so more indexes mean more work per write and more disk used.

What does EXPLAIN tell you that timing the query does not?

It shows the plan — which index was used, whether a full scan happened, and estimated rows — so you can fix the cause instead of just observing the symptom.

What does the A in ACID guarantee in practice?

Atomicity: all writes in the transaction commit together or none do, so a crash midway cannot leave half-updated data behind.

How do RANK and DENSE_RANK differ on ties?

Both give tied rows the same rank. RANK then skips numbers (1, 1, 3), while DENSE_RANK does not (1, 1, 2).

Bonus round — flashcards (+5 XP each)

Define each term out loud before revealing. These count toward your score below.

What is “B-tree index”?

A balanced sorted tree over one or more columns that turns full-table scans into logarithmic lookups, at the cost of slower writes.

What is “EXPLAIN”?

A command that shows the query plan the database chose — indexes used, scan types and row estimates — so you optimise from evidence.

What is “ACID”?

Atomicity, Consistency, Isolation and Durability: the guarantees a transaction makes about grouped writes.

What is “Isolation level”?

How much concurrent transactions can see of each other, from read committed up to serializable.

What is “Window function”?

A function computing over a set of rows related to the current row without collapsing them, like ROW_NUMBER or RANK.

What is “PARTITION BY”?

The clause that splits rows into groups inside a window function, restarting the calculation per group.

7 · Interview ▾

A query is slow on a big table. Walk me through your first steps.

Run EXPLAIN to see the plan, look for a sequential scan or a huge row estimate, check whether an index matches the filter and join columns, add or fix the index, then re-run EXPLAIN to confirm the plan changed.

Explain isolation levels in one minute.

They control what concurrent transactions can see of each other. Read committed hides uncommitted data, repeatable read also freezes rows you have read, and serializable behaves as if transactions ran one by one — safer, but slower and more prone to conflicts.
