Security Rules Deep

Rules are your backend — write them like code, test them like code

Goal — by the end of this lessonBy the end you can write Firestore security rules that enforce owner-only access, validate data shapes on write, use cross-document lookups safely, and explain why rules are not filters.

1. Rules decide every request, allow or deny

▶ YouTube reference — the video for this lesson

Firestore security rules run on Google's servers for every read and write. There is no way around them from a client: if the rules deny it, the data does not move. A rule is a match on a path plus an allow condition. The most important pattern in Skillzify is owner-only access — a signed-in user may read and write only the document whose ID equals their own user ID — which makes the database itself enforce the privacy boundary instead of trusting every client to behave.

2. Validate the shape, not just the identity

▶ YouTube reference — the video for this lesson

Rules can inspect the incoming data, so you can require that XP is a number, that a lesson ID is a string, or that a profile name is under 50 characters. This turns rules into a server-side schema check: a buggy or malicious client cannot write a string where a number belongs, even though it controls the code that sends the write. Keep the checks cheap — every get call inside a rule is a billed read, and rules have a time limit.

3. Rules are not filters

▶ YouTube reference — the video for this lesson

The rule that trips up every beginner: rules cannot hide documents inside a query result. If a query could return a document the rules deny, the whole query fails — Firestore does not silently filter it out. So queries must be written to match the rules: ask only for documents the requester is allowed to see. Design the rules and the queries together, as one system, and test both with the rules emulator before publishing.

▸ Code example — see the Code section below.

Notice the two data objects: request.resource.data is the incoming write, resource.data is the existing document. Confusing them is the most common rules bug.

4 · Code ▾

▶ Run works for JavaScript snippets below — it runs in a sandboxed worker with a 2-second timeout. Python, HTML and CSS snippets are read-only here.

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid} {
      allow read, write: if request.auth != null
        && request.auth.uid == uid
        && request.resource.data.xp is int
        && request.resource.data.xp >= 0;
    }
    match /questions/{qid} {
      allow read: if true;
      allow create: if request.auth != null
        && request.resource.data.authorId == request.auth.uid;
      allow delete: if request.auth != null
        && resource.data.authorId == request.auth.uid;
    }
  }
}

Why does a query fail entirely instead of returning only the allowed documents?

Rules are not filters. If a query could match a denied document, Firestore rejects the whole query — queries must be scoped to documents the requester may read.

What is the difference between resource.data and request.resource.data?

resource.data is the document already stored; request.resource.data is the document as it would look after the write being checked.

7 · Interview ▾

A rule uses get() to check another document — what is the cost and the risk?

Each get() is a billed read and adds latency, and rules have evaluation limits. Overusing cross-document lookups makes rules slow, expensive and fragile.

How do you prove rules are correct before real users depend on them?

Unit-test them with the Firestore rules emulator: scripted allow and deny cases for every role, run in CI, and never publish untested rule edits.
