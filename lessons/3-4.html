Goal — by the end of this lessonBy the end you can design a small REST API with sensible verbs, paths and error shapes, and validate every input as if the client were hostile — because one day it will be.

1. REST in practice

▶ YouTube reference — the video for this lesson

  • Nouns, not verbs, in paths: POST /api/tutor, not /api/askTutorQuestion. The HTTP method carries the verb.
  • Methods mean things: GET reads (no side effects), POST creates/acts, PUT/PATCH updates, DELETE removes.
  • Stateless: each request carries everything the server needs — no hidden session memory of "the last thing you asked".

3. Validation: the server trusts nobody

▶ YouTube reference — the video for this lesson

Client-side validation is a UX nicety; server-side validation is the security boundary. Anyone can call your API with curl, bypassing your UI entirely. So the server checks: is the field present? The right type? Within length limits? Is the mode one of the known 15? Skillzify's server validates mode, message sizes and user IDs on every AI route before spending a single Gemini token.

The cost angleValidation is also cost control: rejecting a 50,000-character "question" before it reaches a paid API is the difference between a hobby bill and a surprise.

Why is client-side validation never sufficient?

Clients are bypassable — anyone can call the API directly with curl or a script. Only server-side checks form a real boundary.

Why keep one error shape across all routes?

So client code handles every failure with a single code path instead of per-route special cases.

6 · Interview

How do you secure an API endpoint beyond authentication?

Validate and size-limit every input server-side, rate limit per IP/user, keep secrets server-side, return consistent errors that leak no internals.

GET vs POST — when does the choice actually matter?

GET must be safe and idempotent (reads, cacheable, appears in logs/URLs); POST is for actions and creations with side effects, like spending an AI call.
