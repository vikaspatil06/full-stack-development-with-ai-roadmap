Testing Basics — Pytest and the Habit of Proof

Prove it works, then change it fearlessly

1. Why test at all

▶ YouTube reference — the video for this lesson

A test is a small program that proves a piece of your code behaves as promised. Without tests, every change is a gamble: you cannot tell whether a fix broke something else until a user finds it. Skillzify's flowchart parser turns code into diagrams — a subtle parser change can silently corrupt output, and only a test suite catches that before learners do.

2. Pytest in five minutes

▶ YouTube reference — the video for this lesson

Install pytest, write functions named test_ in a file named test_*.py, and assert what should be true. Run pytest and it discovers and runs them, reporting passes and failures with the exact assertion that broke. No boilerplate classes, no setup ceremony — a plain function and an assert is a complete test.

▸ Code example — see the Code section below.

3. Parametrize the cases

▶ YouTube reference — the video for this lesson

One test function with @pytest.mark.parametrize runs the same logic over many inputs: boundaries, empty values, weird strings. This is where most bugs hide — at 0, at 1, at the maximum, at the empty case. A test that only checks the happy path proves almost nothing.

4. What to test, and what not to

▶ YouTube reference — the video for this lesson

Test behaviour, not implementation: the function's contract, its edge cases, and its error paths. Do not test the language itself or trivial getters. Aim for the functions where a wrong answer is costly — scoring, parsing, merging, money — and let simple glue code stay untested.

Why test boundary values like 49 and 50 specifically?

Off-by-one errors live at boundaries. A test that only checks 85 can pass while the boundary logic is wrong.

What does pytest.mark.parametrize buy you?

It runs one test function over many inputs, so edge cases get coverage without duplicating test code.

7 · Interview ▾

What is the difference between a unit test and an integration test?

A unit test checks one function in isolation; an integration test checks several pieces working together, like an API route hitting a real database.

How do you decide what deserves a test?

Functions where a wrong answer is costly — scoring, parsing, merging, money — plus edge cases and error paths. Trivial glue can stay untested.
