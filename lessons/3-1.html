1. Node: JavaScript outside the browser

▶ YouTube reference — the video for this lesson

Node.js takes Chrome's V8 JavaScript engine and gives it server powers the browser deliberately withholds: reading files, opening network ports, reading environment variables. Same language, different toolbox — there is no DOM, no document, no localStorage on the server.

2. The event loop: one thread, no waiting around

▶ YouTube reference — the video for this lesson

Node runs your code on a single thread. When code starts a slow operation — reading a file, calling the Gemini API — it registers a callback and moves on instead of blocking. When the operation finishes, its callback joins a queue and the event loop runs it. That is how one small Render instance serves many learners at once: almost all server time is waiting, and Node never waits idle.

The flip side: heavy CPU work in your code (a giant synchronous loop) blocks everyone, because the single thread is busy. Servers must keep handlers light and push waiting to async operations.

Why can one Node process serve many users if it is single-threaded?

Because request handling is mostly waiting on I/O. Async operations register callbacks and free the thread; the event loop runs each callback when its result arrives.

What kind of code is dangerous in a Node handler, and why?

Long synchronous CPU work — it occupies the single thread and blocks every other request until it finishes.

7 · Interview ▾

Explain the Node.js event loop in one minute.

Single thread + async I/O: slow operations register callbacks and release the thread; the event loop picks up completed callbacks from the queue. Concurrency comes from never blocking on waits.

Node vs a traditional threaded server — one trade-off each way?

Node: excellent I/O concurrency with tiny memory, but one CPU-heavy task blocks everyone. Threaded servers isolate CPU work per thread but pay memory and context-switch costs per connection.
