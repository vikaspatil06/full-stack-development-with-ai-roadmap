Testing with Vitest & Jest — Unit and Integration Tests

Proof the code works, not hope

Goal — by the end of this lessonBy the end you can write unit and integration tests with describe, it and expect, mock dependencies, test async code, and read a coverage report without worshipping it.

1. The test pyramid: many small, few big

▶ YouTube reference — the video for this lesson

Tests come in sizes. Unit tests check one function in isolation and run in milliseconds. Integration tests check several pieces together — a route handler plus its validation, for example. End-to-end tests drive the whole app through a browser and are slow and brittle. The pyramid says: many unit tests, fewer integration tests, very few end-to-end tests. Inverting it gives a suite that is slow, flaky and painful to maintain.

Skillzify's Node server currently has no test suite, so every change is verified by hand. The first tests worth writing are the pure, high-risk functions: the rate limiter, the input validation, and the XP and level calculations — the code where a silent bug hurts every learner at once.

2. describe, it, expect: the shape of a test

▶ YouTube reference — the video for this lesson

Vitest and Jest share the same vocabulary. describe groups related tests, it (or test) names one behaviour, and expect asserts an outcome with matchers like toBe, toEqual and toThrow. A good test name reads as a sentence about behaviour: returns 400 when the question is empty. Arrange the inputs, act by calling the code, assert the result — and keep each test about one behaviour so a failure points at one cause.

3. Mocking and testing async code

▶ YouTube reference — the video for this lesson

A mock replaces a real dependency with a controlled fake: a fake Gemini response instead of a live API call, a fixed clock instead of the real time. Mocking keeps tests fast, deterministic and free of network flakiness — but mock the boundaries, not the thing under test, or you end up testing your mocks. Async code is tested by awaiting it: mark the test async and await the promise, or assert with resolves and rejects matchers. A test that forgets to await passes vacuously while the real assertion never runs.

4. Coverage: a map, not a target

▶ YouTube reference — the video for this lesson

Coverage reports which lines and branches your tests executed. It is excellent for finding untested code and useless as a quality score: 100 percent coverage with weak assertions proves nothing, and chasing the last few percent usually means testing trivia. Use coverage to ask where are we blind, then write tests for the risky behaviour there — error paths, boundaries, and the branches a refactor is most likely to break.

4 · Code ▾

▶ Run works for JavaScript snippets below — it runs in a sandboxed worker with a 2-second timeout. Python, HTML and CSS snippets are read-only here.

import { describe, it, expect, vi } from "vitest";

function levelFor(xp) {
  if (xp < 100) return "Beginner";
  if (xp < 300) return "Intermediate";
  return "Advanced";
}

describe("levelFor", () => {
  it("returns Beginner below 100 XP", () => {
    expect(levelFor(50)).toBe("Beginner");
  });
  it("returns Advanced at 300 XP", () => {
    expect(levelFor(300)).toBe("Advanced");
  });
});

Why should most tests be unit tests rather than end-to-end tests?

Unit tests are fast, deterministic and pinpoint failures to one function. End-to-end tests are slow and brittle, so the pyramid keeps them few.

What is the danger of mocking too much?

You end up testing your mocks instead of the real behaviour, so tests pass while the integrated code is broken. Mock only external boundaries like network and time.

Why can an async test pass without testing anything?

If the test does not await the promise, the assertion runs after the test has already finished, so it never actually executes.

What does 100 percent coverage actually prove?

Only that every line ran during the tests — not that the assertions were meaningful. Coverage finds blind spots; it does not measure correctness.

Bonus round — flashcards (+5 XP each)

Define each term out loud before revealing. These count toward your score below.

What is “Test pyramid”?

Many unit tests, fewer integration tests, very few end-to-end tests — a shape that keeps suites fast and failures localised.

What is “Unit test”?

A test of one function or module in isolation, with dependencies replaced by fakes.

What is “Integration test”?

A test of several real pieces working together, like a route handler with its validation and database layer.

What is “Mock”?

A controlled fake replacing a real dependency, used to keep tests fast, deterministic and offline.

What is “Matcher”?

An assertion helper on expect, like toBe, toEqual or rejects, that states the expected outcome.

What is “Coverage”?

A report of which lines and branches tests executed — a map of blind spots, not a quality score.

7 · Interview ▾

What would you test first in an untested codebase?

The pure, high-risk logic with wide blast radius: validation, calculations, rate limits and error paths — the code where one bug affects every user, and which is cheap to unit test.

How do you test code that calls an external API?

Mock the API boundary with a fake response so the test is fast and deterministic, test success and failure shapes, and keep one or two real integration tests separate from the unit suite.
