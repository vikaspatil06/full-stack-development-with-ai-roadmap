Goal — by the end of this lessonBy the end you can read and write owner-only Firestore rules, trace an allowed and a denied request by hand, and sketch Skillzify's data as SQL tables — explaining what each world makes easy.

1. Rules are the real backend security

▶ YouTube reference — the video for this lesson

▸ Code example — see the Code section below.

Read it literally: a request may touch users/{uid} only if it is authenticated and the authenticated identity equals the document's uid. Everyone else — anonymous users, other users, scripts with the public API key — is denied. Rules are evaluated on Google's servers for every request; no client code can bypass them. They are deployed from the Firebase console, and a rules mistake is a data breach, so they are tested before publishing.

2. The same world in SQL

▶ YouTube reference — the video for this lesson

▸ Code example — see the Code section below.

In SQL, access control lives in your server code (every query must filter by the session's user), while structure is enforced by the schema and relationships by foreign keys. You gain joins, aggregations and ad-hoc questions ("average XP per section across all users" is one query in SQL, a project in Firestore) — and you own the server, auth and scaling that Firebase gave you for free.

3. Choosing, honestly

▶ YouTube reference — the video for this lesson

Skillzify's access pattern — "load my stuff, save my stuff" — is Firestore's home turf. The moment the product needs cross-user analytics, leaderboards or complex filtering as core features, SQL earns its keep. Most internships will test SQL; that is why this lesson pairs them.

Production noteSkillzify's community and passport features stay locked until the matching firestore.rules are published in the console — code alone doesn't grant access. Rules are a deployment step, not a file you forget.

rules_version = '2';
service cloud.firestore {
  match /users/{uid} {
    allow read, write: if request.auth != null
                       && request.auth.uid == uid;
  }
}
CREATE TABLE users (id TEXT PRIMARY KEY, name TEXT);
CREATE TABLE progress (
  user_id TEXT REFERENCES users(id),
  lesson_id TEXT,
  xp INT,
  PRIMARY KEY (user_id, lesson_id)

Trace it: user A (uid 'a') requests users/b while signed in. Allowed?

Denied. request.auth.uid ('a') != uid in path ('b'), so the allow condition fails.

Where does access control live in a SQL stack vs Firestore?

SQL: in your server code — every query must scope to the session user. Firestore: in declarative rules evaluated server-side by Google on every request.

7 · Interview ▾

How does Firestore security actually work if the API key is public?

Rules are evaluated server-side per request against request.auth and the target document; the key only identifies the project. Access is granted by rules, never by secrecy.

When would you migrate from Firestore to Postgres?

When core features need relational queries, cross-user aggregation/reporting, or complex filtering that Firestore's index model makes painful — not for fashion.
