1. A coroutine is a lightweight thread you can pause

▶ YouTube reference — the video for this lesson

A coroutine is a computation that can suspend — pause while waiting for a network call or a database read — without blocking its thread, and resume when the result arrives. Thousands of coroutines can share a small pool of threads, which is why Android apps use them for everything asynchronous. The suspend keyword marks functions that may pause, and only another suspend function or a coroutine builder may call them — the compiler enforces the discipline, so asynchronous code cannot accidentally run on the wrong thread.

2. Dispatchers decide where work runs

▶ YouTube reference — the video for this lesson

Three dispatchers cover nearly everything: Main for UI updates, IO for network and disk, Default for CPU-heavy computation. withContext switches dispatcher inside a suspend function, so a Firestore fetch runs on IO and the result returns to Main for display. The classic bug is doing network work on Main — the app freezes — or updating UI from IO — which crashes. Skillzify's Android app fetches the user document on IO and updates the Compose state on Main, and that two-line pattern is most of what dispatchers are for.

3. Structured concurrency: children cannot outlive their parent

▶ YouTube reference — the video for this lesson

Coroutines launched in a scope are children of that scope: when the scope is cancelled, every child is cancelled too. viewModelScope lives as long as the ViewModel, so a sync job started from a screen dies automatically when the screen's ViewModel is cleared — no leaked network calls updating a dead UI. async returns a Deferred you await for parallel work — fetch the user document and the leaderboard concurrently, then combine — and cancellation propagates through await, which is why you should check for it instead of swallowing CancellationException in a generic catch.

▸ Code example — see the Code section below.

Flow is the coroutine answer to streams: a cold flow of values over time, collected in the UI with collectAsStateWithLifecycle, cancelled automatically when the screen leaves.

▶ Run works for JavaScript snippets below — it runs in a sandboxed worker with a 2-second timeout. Python, HTML and CSS snippets are read-only here.

class ProgressViewModel : ViewModel() {
  fun load(uid: String) {
    viewModelScope.launch {
      val user = async(Dispatchers.IO) { repo.getUser(uid) }
      val board = async(Dispatchers.IO) { repo.getLeaderboard() }
      val (u, b) = user.await() to board.await() // parallel, then combine
      _state.value = UiState(u, b) // back on Main automatically
    }
  }
}
// Never catch CancellationException as a generic error: rethrow it.

What does structured concurrency guarantee that raw threads do not?

Child coroutines are tied to their parent scope: cancelling the scope cancels all children, so work cannot outlive the screen or ViewModel that started it.

Why should you never swallow CancellationException in a generic catch?

It is how cancellation propagates. Catching it as an ordinary error breaks structured cancellation and leaves work running after its scope died.

7 · Interview ▾

launch vs async — when is each right?

launch for fire-and-forget work with no result; async when you need the result, usually awaited alongside other parallel calls.

How do you load data in a ViewModel so rotation does not refetch?

Launch in viewModelScope, which survives configuration changes, and expose the result as StateFlow collected by the UI.
