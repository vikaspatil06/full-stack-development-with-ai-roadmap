Data Modelling Patterns

Denormalise on purpose, fan out on write, and know when to stop

Goal — by the end of this lessonBy the end you can choose between embedding and subcollections, design a fan-out write, handle counters that many users update at once, and spot the modelling smell that says a design will not scale.

1. Embed or subcollection: the one question

▶ YouTube reference — the video for this lesson

Every modelling decision in Firestore reduces to one question: is this data bounded and always read with its parent? If yes, embed it in the document. A user profile, streak record and settings live inside users/{uid} because they are small and always loaded together. If the data grows without bound — every question a user ever asked, every event ever logged — it belongs in a subcollection, where it can be queried and paginated independently. An array that grows forever will eventually hit the 1 MiB document limit, and that failure arrives suddenly in production.

2. Denormalise on purpose

▶ YouTube reference — the video for this lesson

NoSQL modelling accepts duplication as the price of fast reads. If the community list shows each question with its author's display name, storing the name on the question document avoids a second read per question. The cost is maintenance: when a user changes their name, every copy must update. That is a fan-out write — one user action updates many documents — and it belongs in a Cloud Function or a batched write, never in code the user can skip.

3. Counters and hot documents

▶ YouTube reference — the video for this lesson

A single counter document that every learner increments — total lessons completed across the site — becomes a hot document: Firestore allows roughly one write per second per document, and concurrent increments start failing. The fix is sharded counters: spread increments across ten counter documents and sum them on read. It is more code, but it is the difference between a feature that works for ten users and one that works for ten thousand.

▸ Code example — see the Code section below.

The same idea applies anywhere many writers hit one document: spread the writes, aggregate on read.

// Sharded counter: pick a shard at random on write, sum on read
const SHARDS = 10;
async function incrementCounter(db, counterId) {
  const shard = Math.floor(Math.random() * SHARDS);
  const ref = doc(db, "counters", counterId + "_" + shard);
  await setDoc(ref, { count: increment(1) }, { merge: true });
}
// Read: fetch all 10 shard docs and add their count fields.

When should data go in a subcollection instead of inside the parent document?

When it grows without bound or needs independent querying and pagination — embedding it would eventually hit the 1 MiB document limit.

Why do high-traffic counters use shards instead of one document?

One document accepts roughly one write per second. Shards spread concurrent writes across many documents, and the total is summed on read.

7 · Interview ▾

Your user changes their display name. What breaks if you denormalised it onto their posts?

Every copy is stale until a fan-out write updates it. You need a reliable update path — a Cloud Function or batched write — or you accept showing the old name.

How do you decide what to denormalise?

By read patterns: duplicate the fields a list view needs so it renders in one query, and only where the update cost of keeping copies fresh is acceptable.
