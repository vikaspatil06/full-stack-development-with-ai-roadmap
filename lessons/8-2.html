Git Branching Strategies

GitHub Flow, Git Flow, trunk-based — and how to pick without a meeting

Goal — by the end of this lessonBy the end you can compare the three main branching strategies, run a feature-branch workflow with pull requests, and resolve a merge conflict without losing work.

1. The three strategies, honestly compared

▶ YouTube reference — the video for this lesson

Git Flow uses long-lived develop and release branches with strict rules — powerful for versioned software with scheduled releases, heavy for a solo project. GitHub Flow is simpler: main is always deployable, every change is a short-lived feature branch merged by pull request — the right default for a continuously deployed web app like Skillzify. Trunk-based development goes further: tiny branches merged within a day, with feature flags hiding unfinished work. The differences are about release cadence and team size, not about which is more correct.

2. The pull request is the unit of review

▶ YouTube reference — the video for this lesson

A feature branch exists to make a change reviewable: one branch, one purpose, a pull request that describes what changed and why. Keep branches small — a pull request touching forty files is reviewed by skimming, which is to say not reviewed at all. Merge with a squash or a merge commit deliberately: squash keeps main's history readable, merge commits preserve the branch's story. Skillzify's history shows the discipline working — one commit per feature, named so the log reads like a changelog.

3. Merge conflicts are normal, not emergencies

▶ YouTube reference — the video for this lesson

A conflict means two branches changed the same lines, and Git cannot decide. Resolve it by reading both versions, choosing the correct combination — often both changes are needed — and testing the result before committing the resolution. Never resolve by accepting one side blindly. Rebase keeps history linear by replaying your branch onto the latest main, but it rewrites commits — fine for your own branch, forbidden for shared ones. The rule is simple: rebase private branches, merge public ones.

▸ Code example — see the Code section below.

Branch naming is a small kindness that pays off in the log: feature/, fix/ and docs/ prefixes tell any reader what a branch is before they open it.

3 · Code

# The GitHub Flow loop, as run daily:
git checkout main && git pull
 git checkout -b feature/mastery-badges
# ... work, commit in small steps ...
git push -u origin feature/mastery-badges
# Open a pull request, get review, squash-merge, delete the branch.
# Conflict? git pull --rebase, resolve markers, git rebase --continue.

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

When is GitHub Flow a better fit than Git Flow?

For continuously deployed apps with a small team, where main is always deployable and releases are frequent — Git Flow's release branches add process with no benefit.

Why must you never rebase a shared branch?

Rebase rewrites commit history. Others who based work on the old commits end up with duplicated, conflicting history.

6 · Interview

Your pull request touches 40 files. What does the reviewer do, and what should you have done?

They skim it and miss things. Split the change into small, separately reviewable pull requests, each with one purpose.

Squash merge vs merge commit — how do you choose?

Squash for a clean, one-commit-per-feature main history; merge commits when the branch's own history is worth preserving. Pick one and stay consistent.
