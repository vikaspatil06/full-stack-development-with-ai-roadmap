WebSockets & Real-Time Apps

When the server needs to speak first

Goal — by the end of this lessonBy the end you can explain when WebSockets beat HTTP polling, build events and rooms with Socket.io, handle heartbeat and reconnection, and describe the scaling limits of real-time connections.

1. HTTP asks, WebSockets converse

▶ YouTube reference — the video for this lesson

HTTP is request-response: the client asks, the server answers, the connection closes. Anything live — a leaderboard updating, a chat message arriving, a collaborator's cursor moving — forces the client to poll repeatedly, wasting requests and still feeling laggy. A WebSocket upgrades one HTTP connection into a persistent two-way channel: either side can send a message at any time, with tiny overhead per message. The rule: if the server needs to speak first, or updates are frequent and small, it is a WebSocket problem.

Skillzify's leaderboard and progress pages currently refresh on page load. A live leaderboard — ranks shuffling as learners earn XP — or a presence indicator showing who is studying now are exactly the features WebSockets exist for.

2. Socket.io: events and rooms

▶ YouTube reference — the video for this lesson

Raw WebSockets give you a pipe; Socket.io gives you a vocabulary. You emit named events with payloads — socket.emit("xp:earned", { xp: 20 }) — and listen with socket.on. Rooms group connections so a message goes only to the right audience: everyone in the lesson:b-1 room hears that lesson's discussion, nobody else does. Socket.io also handles the fallback to long-polling on hostile networks and automatic reconnection, which is why most teams use it instead of the raw API.

3. Heartbeat, reconnection and honest failure

▶ YouTube reference — the video for this lesson

Persistent connections die quietly: laptops sleep, networks drop, proxies time out. A heartbeat — a tiny ping every few seconds, with a pong expected back — detects a dead connection within seconds instead of minutes. On disconnect, the client should reconnect with exponential backoff (wait 1s, then 2s, then 4s, with jitter) rather than hammering a recovering server, and rejoin its rooms and resync any missed state on reconnect. Design for the disconnect, because on real networks it is not an edge case; it is the weather.

4. Scaling real-time: the sticky problem

▶ YouTube reference — the video for this lesson

One server can hold tens of thousands of sockets, but beyond that you need several servers — and a message for a user connected to server B must reach them from server A. The standard answer is a pub/sub backbone like Redis: every server publishes events to shared channels and forwards what its own clients need. Load balancers also need sticky sessions so a client's reconnect lands sensibly. This is the honest cost of real-time: stateful connections are fundamentally harder to scale than stateless HTTP, so use them where liveness is the feature, not by default.

4 · Code ▾

▶ Run works for JavaScript snippets below — it runs in a sandboxed worker with a 2-second timeout. Python, HTML and CSS snippets are read-only here.

import { Server } from "socket.io";

const io = new Server(3000, { cors: { origin: "*" } });

io.on("connection", (socket) => {
  socket.on("lesson:join", (lessonId) => {
    socket.join("lesson:" + lessonId);
  });
  socket.on("xp:earned", ({ lessonId, xp }) => {
    io.to("lesson:" + lessonId).emit("xp:update", { xp });
  });
  socket.on("disconnect", () => {
    console.log("client left", socket.id);
  });
});

When do WebSockets beat HTTP polling?

When the server must push updates promptly or messages are frequent and small. Polling wastes requests and still lags; a WebSocket keeps one open channel for instant two-way messages.

What is a Socket.io room for?

It groups connections so an event reaches only the relevant audience — everyone viewing one lesson, for example — instead of broadcasting to all clients.

Why use exponential backoff on reconnect?

It spaces retries out so thousands of clients do not hammer a recovering server at the same instant, while still reconnecting quickly after brief drops.

Why is scaling WebSockets harder than scaling HTTP?

Connections are stateful and long-lived, so messages must be routed to the specific server holding each client, usually via a pub/sub backbone like Redis and sticky sessions.

Bonus round — flashcards (+5 XP each)

Define each term out loud before revealing. These count toward your score below.

What is “WebSocket”?

A persistent two-way connection upgraded from HTTP, letting either side send messages at any time with low overhead.

What is “Polling”?

Repeatedly asking the server for updates over HTTP — simple, but wasteful and laggy compared with a push channel.

What is “Socket.io event”?

A named message with a payload, sent with emit and received with on, forming the vocabulary of a real-time app.

What is “Room”?

A named group of connections that receive events together, like everyone viewing one lesson.

What is “Heartbeat”?

Periodic ping/pong messages that detect dead connections quickly so they can be cleaned up and reconnected.

What is “Pub/sub backbone”?

A shared message bus like Redis that relays events between multiple WebSocket servers so any client can be reached.

7 · Interview ▾

Design a live leaderboard. How do updates reach every viewer?

Clients open WebSocket connections and join a leaderboard room. When XP changes, the server emits an update event to the room; at scale, servers relay through Redis pub/sub so every connected viewer hears it.

How do you detect a dead WebSocket connection?

With a heartbeat: periodic pings expecting pongs within a timeout. No pong means the connection is dead, so the server cleans it up and the client reconnects with backoff.
