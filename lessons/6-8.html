Performance Profiling

Measure first: long tasks, layout thrash, and the bundle that ate the page

1. Measure, then optimise — never the reverse

▶ YouTube reference — the video for this lesson

Performance work without measurement is superstition. The Performance panel records what the browser actually does — scripting, rendering, painting — on a timeline you can inspect frame by frame. A long task is any JavaScript block over 50 milliseconds, and it is what users feel as a frozen button or a stuttering scroll. The first trace usually surprises: the slow part is rarely the code you suspected. Skillzify's lesson list rendering, for example, is fast — the expensive part is usually a third-party script or an oversized image nobody measured.

2. The usual suspects

▶ YouTube reference — the video for this lesson

Four patterns cause most slowness. Long tasks block the main thread — split them with chunking or move them to a worker, exactly as Pyodide already is. Layout thrash happens when code reads a layout value then writes a style in a loop, forcing the browser to recalculate layout every iteration — batch reads, then batch writes. Oversized images and fonts delay first paint — serve sized images and preload only the font weights you use. And a large JavaScript bundle delays interactivity — load Pyodide and CodeMirror lazily, only on the pages that need them.

3. Lighthouse and real-user metrics

▶ YouTube reference — the video for this lesson

Lighthouse gives a lab score and a prioritised list — it is a starting point, not a verdict. The numbers that matter in production are the Core Web Vitals: how fast the largest content paints, how much the layout shifts, and INP — Interaction to Next Paint — how quickly the page responds to a tap. INP is the one users feel most directly: a button that takes 300 milliseconds to respond feels broken, whatever the Lighthouse score says.

▸ Code example — see the Code section below.

Profile on a slow device or with CPU throttling — your development machine hides the problems your users feel on a budget phone.

// Find long tasks in the wild, not just in the lab
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 50) {
      console.warn("Long task:", Math.round(entry.duration), "ms");
    }
  }
});
observer.observe({ entryTypes: ["longtask"] });

What is a long task, and why does 50ms matter?

A JavaScript block over 50ms on the main thread; beyond that, taps and scrolls visibly stall because the browser cannot respond while the task runs.

What is INP in one sentence?

How quickly the page visibly responds after a user interaction — the responsiveness number users actually feel.

7 · Interview ▾

Lighthouse says 95 but users on cheap phones complain it feels slow. What do you trust?

The users. Lighthouse runs in lab conditions; real-device traces and field INP data reflect the throttled CPUs and networks your users actually have.

What causes layout thrash, and what is the fix?

Alternating layout reads and style writes in a loop, forcing a recalculation each time. Fix: batch all reads first, then all writes.
