1. Three pieces: entity, DAO, database

▶ YouTube reference — the video for this lesson

Room is a thin, compile-time-checked layer over SQLite. An entity is a data class annotated with its table name — each field a column, the primary key declared explicitly. A DAO is an interface whose methods carry SQL annotations: @Query for reads, @Insert and @Update for writes. The database class ties entities and DAOs together. The compiler verifies your SQL against the schema at build time, so a typo in a column name fails the build instead of crashing on a user's phone — Room's single biggest advantage over raw SQLite.

2. Coroutines and Flow are the API

▶ YouTube reference — the video for this lesson

DAO methods are suspend functions for one-shot work and Flow for streams: a query returning Flow of lessons re-emits automatically whenever the underlying table changes, so the UI stays current without manual refreshes. Writes run on a background dispatcher, and Room forbids main-thread database access by default — the crash you get for trying is the framework protecting you from freezing the UI. Skillzify's Android app can cache the user document locally in Room so the app opens instantly and syncs in the background, the offline-first pattern from Module 4 made concrete.

3. Migrations: never wipe user data

▶ YouTube reference — the video for this lesson

Changing the schema — adding a column, renaming a table — requires a migration: a version bump plus SQL that transforms the old data into the new shape. The fallback, destructive migration, deletes the whole database and every learner's cached progress with it. Write the migration, test it against a database created with the old version, and keep the schema export files in version control so Room can verify migrations automatically. Data loss is not a bug users forgive.

▸ Code example — see the Code section below.

Room's rule of thumb: the database is the source of truth for what is on screen; the network is how it gets refreshed.

▶ Run works for JavaScript snippets below — it runs in a sandboxed worker with a 2-second timeout. Python, HTML and CSS snippets are read-only here.

@Entity(tableName = "lessons")
data class LessonEntity(
  @PrimaryKey val id: String,
  val title: String,
  val section: String,
  val done: Boolean = false
)

@Dao
interface LessonDao {
  @Query("SELECT * FROM lessons WHERE section = :section")
  fun bySection(section: String): Flow<List<LessonEntity>>
  @Insert(onConflict = OnConflictStrategy.REPLACE)
  suspend fun insertAll(lessons: List<LessonEntity>)
}

What does Room check at compile time that raw SQLite cannot?

Your SQL against the schema — a wrong column or table name fails the build instead of crashing at runtime.

Why is a destructive migration unacceptable for a learning app?

It deletes the database, wiping every learner's cached progress and offline data. A real migration preserves it.

7 · Interview ▾

When would you expose Flow from a DAO instead of a suspend function?

When the UI must stay current: Flow re-emits on every table change, so the screen updates without manual refresh logic.

How does offline-first change your repository design?

The database becomes the source of truth for the UI; the network refreshes it in the background, and writes go to the database first, then sync.
