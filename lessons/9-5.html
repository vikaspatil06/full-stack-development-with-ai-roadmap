System Design Basics for Interviews

Requirements first, boxes second

Goal — by the end of this lessonBy the end you can walk through a system design interview in order — requirements, scale estimates, API, data model, caching and queues — and talk through trade-offs out loud.

1. Start with requirements, not boxes

▶ YouTube reference — the video for this lesson

Every design interview opens the same way: clarify what the system must do before drawing anything. Functional requirements are the features — shorten a URL, redirect to the original, count clicks. Non-functional requirements are the qualities — how many users, how fast, how available, how consistent. Skipping this step is the most common failure: candidates design for a scale and a feature set nobody asked for. Spend the first minutes asking questions and writing the requirements down where the interviewer can see them.

2. Estimate the scale, then design the API and data

▶ YouTube reference — the video for this lesson

Rough numbers drive every later decision. A URL shortener with 100 million new links a month writes about 40 per second but might read 4,000 per second — a read-heavy system, which immediately suggests caching. Then define the API: POST /shorten with a long URL returns a short code, GET /{code} redirects. Then the data model: one table mapping code to long URL, plus a clicks counter. The short code itself is usually a base-62 encoding of an auto-incrementing id, which guarantees uniqueness without checking.

3. Caching, queues and the scaling levers

▶ YouTube reference — the video for this lesson

Three levers solve most scaling questions. Caching stores hot data close to the reader: popular short links in Redis, so most redirects never touch the database — the trade-off is staleness when data changes. Queues move slow work off the request path: click analytics go onto a queue and are processed asynchronously, so the redirect stays fast. Horizontal scaling adds more stateless servers behind a load balancer, which works precisely because the servers hold no session state. Name the lever, then name its cost — that pairing is what interviewers listen for.

4. Talking through trade-offs

▶ YouTube reference — the video for this lesson

There is no single right answer in system design, only justified ones. For every choice, say what you gain and what you give up: a cache buys latency and costs freshness; a queue buys responsiveness and costs complexity; strong consistency buys correctness and costs availability under failure. Skillzify makes the same calls at small scale — Firebase for auth and data instead of running its own database, Render for hosting instead of managing servers. Being able to explain why those were reasonable choices at that scale is the whole skill, scaled up.

6 · Check ▾

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each — or “Didn’t know it” to count it as a miss. Your score shows below.

Why clarify requirements before drawing any architecture?

Scale and feature decisions depend on them. Designing before knowing the read/write ratio or latency needs means optimising for a system nobody asked for.

Why is base-62 encoding of an id a good short-code strategy?

Ids are unique by construction, so encoding them gives unique codes with no collision checks, and base-62 keeps the codes short using letters and digits.

What does a cache cost you, in one word?

Freshness: cached data can be stale after the underlying value changes, so you trade correctness-at-this-instant for speed.

Why must servers be stateless to scale horizontally?

A load balancer can send any request to any server, so no server can hold session data another server would need. State moves to the database or cache.

Bonus round — flashcards (+5 XP each)

Define each term out loud before revealing. These count toward your score below.

What is “Functional requirements”?

What the system must do: the features and behaviours users can observe.

What is “Non-functional requirements”?

How well it must do it: scale, latency, availability and consistency targets.

What is “Scale estimate”?

Rough arithmetic — users, requests per second, storage — that decides which design levers are needed.

What is “Cache”?

A fast store for hot data, like Redis, that trades freshness for latency on read-heavy paths.

What is “Queue”?

A buffer that moves slow work off the request path for asynchronous processing, trading simplicity for responsiveness.

What is “Horizontal scaling”?

Adding more stateless servers behind a load balancer instead of making one server bigger.

7 · Interview ▾

Design a URL shortener. Where do you start?

Requirements first: shorten, redirect, click counts, and the expected scale. Then estimate reads versus writes, define the API, choose the data model and code generation, and add caching for hot links with a stated staleness trade-off.

When would you add a queue to a design, and what does it cost?

When work is slow or bursty and does not need to finish inside the request — analytics, emails, image processing. It costs complexity: retries, ordering and failure handling become your problem.
