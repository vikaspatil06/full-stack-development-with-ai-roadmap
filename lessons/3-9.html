REST vs GraphQL — Choosing How Clients Ask for Data

One endpoint per resource, or one endpoint for everything

Goal — by the end of this lessonBy the end you can explain REST and GraphQL, compare them honestly, and defend why Skillzify's API is REST.

1. REST: resources and verbs

▶ YouTube reference — the video for this lesson

REST organises an API around resources with URLs and HTTP verbs: GET /lessons lists lessons, GET /lessons/b-1 fetches one, POST /lessons creates one. Responses are fixed shapes, caching works through HTTP, and every tool from browsers to curl understands it. Skillzify's API is REST because its operations are simple, its clients are few, and HTTP caching and status codes do most of the work for free.

2. GraphQL: the client asks for exactly what it needs

▶ YouTube reference — the video for this lesson

GraphQL exposes one endpoint where the client sends a query describing precisely the fields it wants, nested as deep as needed. A mobile screen that needs a lesson title, its section name and the author's name gets all three in one request instead of three round trips. The cost is a schema to maintain, resolvers to write, and caching that no longer comes free from HTTP.

▸ Code example — see the Code section below.

3. The real trade-offs

▶ YouTube reference — the video for this lesson

REST over-fetches (you get fields you did not ask for) and under-fetches (you need several requests for nested data). GraphQL fixes both but adds complexity: query depth limits to prevent abuse, resolver performance to watch, and a learning curve for every consumer. For a small team with a simple API, REST wins; for many clients with wildly different data needs, GraphQL earns its keep.

4. The interview answer

▶ YouTube reference — the video for this lesson

Do not pick a side — pick a fit. Skillzify chose REST because its API is a handful of endpoints serving one web app and one Android app, and simplicity beats flexibility there. Being able to name the trade-off and the threshold where you would switch is the senior answer.

3 · Code

# REST: three requests for nested data
GET /lessons/b-1

GET /users/42

# GraphQL: one query, exactly the fields wanted
{
  lesson(id: "b-1") {
    title
    section { name }
    author { name }
  }
}

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

What problem does GraphQL solve that REST does not?

Over-fetching and under-fetching: the client requests exactly the fields it needs, nested, in a single request instead of several round trips.

What does GraphQL lose compared to REST?

Free HTTP caching, simple status codes, and simplicity — it needs a schema, resolvers, and query-depth protection against abuse.

6 · Interview

When would you choose GraphQL over REST?

When many different clients need different shapes of the same data and nested fetching causes many round trips — and the team can afford the schema and tooling.

Why is Skillzify's API REST?

A handful of endpoints, two clients, simple operations — HTTP caching and status codes cover the needs, and REST keeps the server simple to reason about.
