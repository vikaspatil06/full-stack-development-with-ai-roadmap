1. Anatomy of a workflow

▶ YouTube reference — the video for this lesson

▸ Code example — see the Code section below.

on is the trigger, jobs are machines, steps are commands or reusable actions. Skillzify's real workflow follows exactly this shape: JDK 17, Gradle 8.10.2, assemble the arm64 debug APK on every push to main. Green check = the app builds from a clean machine, which is the only build result that counts.

2. The supporting cast

▶ YouTube reference — the video for this lesson

  • CodeQL — static security analysis on push/PR + weekly, across JS/TS, Python and Java/Kotlin in Skillzify's setup.
  • Dependabot — watches dependencies and opens PRs for updates/vulnerabilities. Skillzify runs alerts + dependency graph with auto security updates deliberately off — a human reviews each bump.
  • Secrets — CI credentials live in repo settings, injected as env vars, masked in logs. Same doctrine as Lesson 3.4, second home.

3. Reading failures like a professional

▶ YouTube reference — the video for this lesson

Open the failed step, find the first real error (the rest is cascade), reproduce locally with the same command, fix, push. Skillzify's CI history includes a run of failures caused by mixing Gradle DSL dialects — the lesson generalises: most CI failures are environment or config, not your feature code.

CI is a promise"Works on my machine" is not a build. If Actions can't build it from a cold checkout, it doesn't ship — that discipline is what makes the green check meaningful in interviews and teams.

3 · Code

name: Build APK
on: { push: { branches: [ main ] } }
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: "17", distribution: "temurin" }
      - run: cd android && ./gradlew assembleArm64Debug

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

What do on, jobs and steps mean in a workflow file?

on = the triggering event; jobs = isolated runner machines that execute work; steps = the ordered commands/actions inside a job.

Your CI fails but the code works locally. First three suspects?

Environment differences (versions, OS), missing env vars/secrets, and config/DSl mistakes — in that order, before suspecting feature code.

6 · Interview

Explain your project's CI pipeline.

On push to main, Actions checks out the repo, sets up JDK 17, builds the arm64 debug APK with Gradle; CodeQL scans weekly and Dependabot watches dependencies. Green build from a clean runner is the ship gate.

Where do CI secrets live and how are they used?

In repository/organisation secret settings, injected as environment variables at runtime and masked in logs — never in the workflow file or the repo.
