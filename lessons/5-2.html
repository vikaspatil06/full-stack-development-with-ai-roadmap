Tokens & Context Windows

The unit everything in LLM pricing and prompting is measured in

1. What a token actually is

▶ YouTube reference — the video for this lesson

A token is a chunk of text — roughly three quarters of an English word on average. The model never sees words or letters; it sees token IDs produced by a tokenizer that splits text by frequency, so common words become one token and rare words splinter into several. That is why counting characters is a poor estimate of cost: the same sentence can cost different tokens depending on the words in it, and code, with its symbols and indentation, tokenizes far less efficiently than prose. Every price, limit and quota in the LLM world is denominated in tokens, so this unit is the budget you actually manage.

2. The context window is a hard wall

▶ YouTube reference — the video for this lesson

The context window is the maximum number of tokens the model can consider in one request — prompt plus reply combined. Exceed it and the request fails outright; there is no graceful overflow. Gemini's large windows invite a lazy habit — paste everything — which costs money on every call and degrades answer quality, because the model attends less precisely to any one fact when the window is stuffed. The disciplined move is to send the smallest context that answers the question: a retrieved lesson excerpt, not the whole curriculum.

3. Counting before you send

▶ YouTube reference — the video for this lesson

Count tokens before the call, not after the bill. Gemini's countTokens endpoint exists precisely for this, and Skillzify's server should use it to enforce caps before spending anything. Rough mental math works too: about 4 characters per token for English, worse for code. Track three numbers per feature — tokens in, tokens out, and cost per call — and every pricing or cap decision becomes arithmetic instead of guesswork.

▸ Code example — see the Code section below.

Output tokens cost more than input tokens on most models, so a rambling reply is also a budget line — ask for concise formats and set max output tokens per mode.

// Estimate and enforce before spending: count, then cap
const count = await model.countTokens({
  contents: [{ role: "user", parts: [{ text: prompt }] }]
});
console.log("prompt tokens:", count.totalTokens);

if (count.totalTokens > 8000) {
  prompt = summariseOrTruncate(prompt); // never send blind
}
// Rule of thumb: ~4 chars per token for English, ~2-3 for code.

Why is character count a bad way to estimate token cost?

Tokenizers split by frequency: common words are one token, rare words and code splinter into several, so identical lengths can cost very different token counts.

What happens when prompt plus reply exceed the context window?

The request fails. There is no graceful overflow, so you must count and trim before sending.

7 · Interview ▾

How do you keep LLM costs predictable in a product with free users?

Count tokens before each call, enforce per-user daily caps server-side, prefer small retrieved context over full-document pastes, and cap output tokens per mode.

Why does stuffing the context window hurt answer quality, not just cost?

Attention dilutes: with more context the model weighs any single fact less precisely, so long prompts often produce vaguer answers than focused ones.
