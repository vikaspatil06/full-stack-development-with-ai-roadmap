Docker Compose & Production Containers

One command, the whole stack

Goal — by the end of this lessonBy the end you can define a multi-service app in Docker Compose, persist data with volumes, configure services with environment variables, and shrink images with multi-stage builds.

1. Compose: many containers, one file

▶ YouTube reference — the video for this lesson

A real app is rarely one container: a web server, a database, a cache, maybe a worker. Docker Compose describes all of them in one docker-compose.yml file — services, the image or build for each, ports to publish, and the network they share. One command, docker compose up, starts the whole stack in the right order, and service names double as hostnames, so the app reaches the database at db:5432 without any IP addresses. This is the file that turns it works on my machine into it works everywhere.

2. Volumes: data that outlives containers

▶ YouTube reference — the video for this lesson

Containers are disposable: delete one and its filesystem goes with it. Volumes solve this by mounting storage that lives outside the container lifecycle. A named volume holds the database's data directory, so rebuilding the database container keeps every row. Bind mounts instead map a folder from your machine into the container, which is ideal in development for live code changes and risky in production, where the host layout should not leak into the app. Rule of thumb: named volumes for data, bind mounts for development code.

3. Environment variables and configuration

▶ YouTube reference — the video for this lesson

Configuration belongs outside the image: the same image should run in development, staging and production with only its environment changed. Compose sets variables per service with environment or an env_file, and secrets stay in a .env file that is never committed. Skillzify follows exactly this discipline on Render — its Gemini key lives in environment variables, not in the repository — and a containerised version would keep the same rule, just delivered through Compose instead of a dashboard.

4. Multi-stage builds and image size

▶ YouTube reference — the video for this lesson

Every layer in an image adds size and attack surface. A multi-stage Dockerfile builds in a fat stage with compilers and dev dependencies, then copies only the finished artifact into a slim runtime stage. A Node app that builds at 900 MB can ship at 150 MB, which deploys faster and exposes less. Pin base image versions, add a .dockerignore so node_modules and secrets never enter the build, and run as a non-root user. Skillzify currently deploys to Render from a Git repository; containers would make that deploy reproducible on any host, at the cost of owning the image pipeline.

Why do services in Compose reach each other by name?

Compose creates a shared network where each service name resolves as a hostname, so the app connects to db:5432 without hardcoding addresses.

What happens to data written inside a container without a volume?

It disappears when the container is removed. Volumes keep data outside the container lifecycle so it survives rebuilds.

Why keep secrets in environment variables instead of the image?

Images get shared and cached; a secret baked in leaks to anyone with the image. Environment variables let the same image run everywhere with different secrets.

What does a multi-stage build achieve?

It builds with full tooling in one stage and copies only the artifact into a slim runtime image, shrinking size and attack surface.

Bonus round — flashcards (+5 XP each)

Define each term out loud before revealing. These count toward your score below.

What is “Docker Compose”?

A tool that defines and runs multi-container apps from one YAML file: services, networks, ports and volumes.

What is “Service”?

One container definition in Compose — an image or build, plus its ports, environment and dependencies.

What is “Named volume”?

Docker-managed persistent storage mounted into a container, surviving container deletion — where database data belongs.

What is “Bind mount”?

A host folder mapped into a container; ideal for live development, a liability in production.

What is “Multi-stage build”?

A Dockerfile with a build stage and a slim runtime stage, copying only the finished artifact across.

What is “.dockerignore”?

A file listing paths excluded from the build context, keeping node_modules and secrets out of images.

7 · Interview ▾

Explain the difference between a named volume and a bind mount.

A named volume is Docker-managed storage that persists data across containers — right for databases. A bind mount maps a host folder into the container — right for live development, risky in production.

How do you make a Docker image production-ready?

Multi-stage build for a slim runtime, pinned base versions, a .dockerignore, non-root user, configuration via environment, and healthchecks so orchestrators know when it is actually ready.
