Workflows, caching, matrices, and the deploy gate that saves you

1. A workflow is a recipe that runs on every push

▶ YouTube reference — the video for this lesson

Continuous integration means every push triggers an automated pipeline: check out the code, install dependencies, run tests, build the artefact. GitHub Actions expresses that pipeline as YAML — a workflow file with triggers, jobs and steps. Jobs run on fresh virtual machines and can run in parallel; steps run in order inside a job. Skillzify's Android workflow installs JDK 17 and Gradle, then builds the debug APK — the same commands you would run locally, executed by a machine that never forgets a step and never has a different environment.

2. Caching and matrices: speed and coverage

▶ YouTube reference — the video for this lesson

Two features separate a tolerable pipeline from a good one. Caching stores dependency downloads between runs — Gradle and npm caches turn a five-minute install into thirty seconds — keyed by the lockfile so a dependency change busts the cache automatically. A matrix runs the same job across combinations — Node 18 and 20, or several API levels — so one workflow file tests the whole support range. Both are cheap to add and compound over hundreds of runs.

3. Secrets, artefacts, and the deploy gate

▶ YouTube reference — the video for this lesson

Secrets live in the repository settings, are masked in logs, and are only exposed to the steps that need them — never printed, never committed. Artefacts are the pipeline's outputs: the built APK or the test report, stored for download. The deploy gate is the discipline: the deploy job depends on the test job succeeding, so a red build cannot reach production. Skillzify's Render deploy is manual for exactly this reason — a human decides when green means go — and the pipeline's job is to make that decision easy and evidence-based.

A pipeline you trust changes how you work: small commits, pushed often, because the machine catches what you missed within minutes.

4 · Code ▾

▶ Run works for JavaScript snippets below — it runs in a sandboxed worker with a 2-second timeout. Python, HTML and CSS snippets are read-only here.

# .github/workflows/ci.yml — test on every push, deploy only when green
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npm test
  deploy:
    needs: test # blocked unless tests pass
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - run: echo "Deploy step runs only on green main"

Why key a dependency cache on the lockfile?

So a dependency change automatically busts the cache — the key changes, the old cache is ignored, and the install is fresh. A stale cache would test old dependencies.

What does needs: test do in a deploy job?

It makes deployment depend on the test job succeeding, so a red build can never reach production.

7 · Interview ▾

Your CI is slow and developers stop waiting for it. What do you fix first?

Caching and parallel jobs — the biggest wins are usually dependency caching and splitting tests across jobs, not faster machines.

How do you keep secrets safe in CI?

Store them in the provider's secret store, expose them only to the steps that need them, never print them, and rotate immediately if one ever appears in a log.
