1. The mental model: documents in collections

▶ YouTube reference — the video for this lesson

Firestore is not tables and rows. A collection holds documents; each document is a JSON-like object with fields, and can contain subcollections. You design around how the app reads, not around normalised purity — duplication is acceptable, joins are not a thing.

2. One document per user: Skillzify's core decision

▶ YouTube reference — the video for this lesson

▸ Code example — see the Code section below.

Why one doc? The app always loads everything about me at sign-in — one read, no queries. Web and Android read and write the same document, which is what makes cross-device sync (Lesson 4.3) even possible. The cost: a document has a 1 MiB limit and hot-document write contention — fine for one learner's progress, wrong for a global leaderboard counter.

3. Design rules of thumb

▶ YouTube reference — the video for this lesson

  • Model for your reads: if the UI shows it together, store it together.
  • Keep documents bounded: arrays that grow forever eventually need subcollections.
  • Every query needs its fields indexed in mind: Firestore can only filter/sort on what it can index — no "search anywhere" queries.
The contrast to carry into SQL (Lesson 4.4)SQL normalises to remove duplication and answers unplanned questions with joins. Firestore denormalises for planned reads and punishes unplanned ones. Neither is "better" — they optimise opposite things.

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

Why does Skillzify store all of a user's progress in a single document?

The app always loads the whole user state at sign-in — one read, no queries — and web/Android sync the identical document.

Name one workload where the one-document design fails.

Anything unbounded or globally shared: ever-growing arrays hit the 1 MiB doc limit, and many writers on one doc (like a global counter) hit write contention.

6 · Interview

How do you decide between embedding data in a document vs a subcollection?

Embed when data is bounded and always read with the parent; use a subcollection when it grows unboundedly or needs independent querying/pagination.

Firestore or Postgres for a new startup app — how do you choose?

By access patterns and team: Firestore for simple, user-scoped, realtime-ish reads and zero ops; Postgres when relationships, complex queries, reporting or strict consistency dominate.
