SQL Joins & Aggregates

The two ideas that make relational databases worth learning

Goal — by the end of this lessonBy the end you can write INNER and LEFT JOINs, use GROUP BY with COUNT, SUM and AVG, filter groups with HAVING, and translate a Skillzify Firestore model into tables with foreign keys.

1. Joins stitch tables at read time

▶ YouTube reference — the video for this lesson

SQL stores data normalised — one fact in one place — and reassembles it when you ask. An INNER JOIN returns only rows that match on both sides: lessons joined to their completions give you only lessons someone finished. A LEFT JOIN keeps every row from the left table even when there is no match, so you can list all lessons with a completion count that is zero for untouched ones. That difference is the single most-tested SQL idea, and it maps directly to a question Firestore cannot answer at all: show me everything, including the things with no activity.

2. Aggregates answer questions about groups

▶ YouTube reference — the video for this lesson

COUNT, SUM and AVG collapse many rows into one number, and GROUP BY runs them per group instead of for the whole table: total XP per user, average quiz score per section, lessons completed per day. WHERE filters rows before grouping; HAVING filters groups after — users with more than 100 XP, sections averaging below 50 percent. Mixing those two up is the classic aggregate mistake, and interviewers ask it precisely because it reveals whether you understand the order SQL executes in.

3. The same schema, two shapes

▶ YouTube reference — the video for this lesson

Skillzify's users/{uid} document becomes a users table plus a completions table with a foreign key back to the user, and an exercises table keyed by user and exercise. Nothing is duplicated: the display name lives in one row. The price is that every read is now a join, and every new question needs a new query — the exact trade-off Firestore made in the opposite direction. Neither shape is correct in general; the right one follows from your read patterns.

▸ Code example — see the Code section below.

Read the second query out loud: lessons are the left side, completions may or may not exist, and COUNT of the joined key is zero when nothing matched — that is the LEFT JOIN doing its job.

3 · Code

-- Average quiz score per section, only for sections with 5+ attempts
SELECT section, AVG(score) AS avg_score, COUNT(*) AS attempts
FROM quiz_attempts
GROUP BY section
HAVING COUNT(*) >= 5
ORDER BY avg_score ASC;

-- All lessons with completions, including never-attempted ones
SELECT l.title, COUNT(c.user_id) AS completions
FROM lessons l
LEFT JOIN completions c ON c.lesson_id = l.id
GROUP BY l.id, l.title;

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

What is the difference between INNER JOIN and LEFT JOIN?

INNER JOIN keeps only rows with a match on both sides; LEFT JOIN keeps every row from the left table and fills unmatched columns with null.

WHERE vs HAVING — which filters groups, and why does the order matter?

HAVING filters groups after GROUP BY and aggregation; WHERE filters individual rows before grouping, so it cannot use aggregate results.

6 · Interview

Why does SQL normalise while Firestore denormalises?

SQL is built for ad-hoc questions answered at read time with joins, so one copy of each fact is best. Firestore is built for planned reads with no joins, so data is duplicated to make each read cheap.

A query is slow on a large table. What do you check first?

Whether the filtered and joined columns are indexed, and the query plan — a missing index turns a lookup into a full table scan.
