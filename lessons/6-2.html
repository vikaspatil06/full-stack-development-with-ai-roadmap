Real Python in the browser: workers, packages, and the JS bridge

1. Pyodide is CPython compiled to WebAssembly

▶ YouTube reference — the video for this lesson

Pyodide is the real CPython interpreter, compiled to WebAssembly so it runs entirely in the browser — no server, no sandbox account, no per-run cost. That is why Skillzify's Code Studio can run learner code instantly and offline: the runtime downloads once, then every run is local. The trade-off is size and startup time — the runtime is several megabytes — so you load it once, lazily, and show honest loading state instead of pretending it is instant.

2. Run it in a Worker, never on the main thread

▶ YouTube reference — the video for this lesson

Python code can loop forever, and a loop on the main thread freezes the whole page. The fix is a Web Worker: Pyodide lives in a separate thread, the UI stays responsive, and you can terminate the worker when code runs too long. Communication is message-passing — the main thread sends code, the worker sends back output, errors and a done signal. Skillzify's compiler is this architecture: the editor is the UI, the worker is the machine.

3. The bridge: stdout, packages, and data

▶ YouTube reference — the video for this lesson

Three bridge details make it feel like a real environment. First, capture stdout by redirecting Python's print output into a buffer the worker returns as text. Second, install packages with micropip — loadPackage for the bundled scientific stack, micropip.install for pure-Python packages from PyPI — and cache them so the second run is fast. Third, move data across the bridge with toJs and fromJs: Python lists become JS arrays, dicts become Maps, and proxies must be destroyed or they leak memory.

▸ Code example — see the Code section below.

Guard the worker with a timeout — terminate and respawn after a few seconds — because an infinite loop has no other off switch.

3 · Code

// Inside the worker: load once, run many times
importScripts("https://cdn.jsdelivr.net/pyodide/v0.26.4/full/pyodide.js");
let pyodideReady = loadPyodide();

onmessage = async (e) => {
  const pyodide = await pyodideReady;
  pyodide.setStdout({ batched: (s) => postMessage({ type: "out", text: s }) });
  try {
    await pyodide.loadPackage("numpy"); // or micropip.install("requests")
    const result = await pyodide.runPythonAsync(e.data.code);
    postMessage({ type: "done", result: String(result) });
  } catch (err) {
    postMessage({ type: "error", text: String(err.message) });
  }
};
// Main thread: new Worker("pyodide-worker.js"), post code, kill on timeout.

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

Why must Pyodide run in a Web Worker instead of the main thread?

Python code can loop forever; on the main thread that freezes the page. A worker keeps the UI responsive and can be terminated on timeout.

How do you get print output out of Pyodide and into your page?

Redirect Python stdout with setStdout and forward each batch to the main thread as a message, which appends it to the output pane.

6 · Interview

Pyodide vs running Python on a server — when is each right?

Pyodide for instant, free, offline-capable runs of learner code; a server for untrusted code at scale, heavy packages, or work that must not depend on the user's device.

What leaks if you pass Python objects to JavaScript carelessly?

PyProxy objects wrap Python values; if you never destroy them they hold Python objects alive and leak memory. Convert with toJs or destroy the proxy.
