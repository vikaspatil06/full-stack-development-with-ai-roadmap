Error Handling & Logging — When Things Go Wrong in Production

Fail loudly to yourself, kindly to the user

1. Errors need a shape

▶ YouTube reference — the video for this lesson

Every API error should look the same: a status code, a short machine-readable code, and a human message. Clients can then handle errors by code instead of parsing English sentences. Skillzify's API returns { error: "Daily cap reached" } with a 429 — the frontend shows exactly that message, and the code never has to guess what went wrong.

2. One error handler, everywhere

▶ YouTube reference — the video for this lesson

Express error middleware with four arguments is the single funnel: log the full error with a request id, then send a safe response. Validation errors get a 400 with specifics; unexpected errors get a 500 with a generic message. Never send err.stack or database messages to the client — they hand attackers a map of your internals.

▸ Code example — see the Code section below.

3. Logging that helps at 2am

▶ YouTube reference — the video for this lesson

A useful log line has a timestamp, a level (info, warn, error), a request id that ties lines together, and the key facts: route, user id, what failed. Structured JSON logs can be searched and filtered; free-text logs cannot. On Render's free tier, logs are your only window into production — make each line earn its place.

4. Graceful degradation

▶ YouTube reference — the video for this lesson

When the AI backend is down, Skillzify shows a friendly fallback instead of a blank screen or a crash. Design every feature with its failure mode: what does the user see, what still works, and what gets logged so you can fix it. A feature that fails gracefully is a feature that survives production.

app.use(function (err, req, res, next) {
  console.error(req.id, err.stack);   // full detail: server logs only
  const status = err.status || 500;
  res.status(status).json({
    error: status === 500 ? "Something went wrong" : err.message
  });
});

Why must a 500 response never include err.stack?

A stack trace reveals file paths, library versions and internals that help an attacker. The client needs a generic message; the detail belongs in server logs.

What makes a log line useful when debugging production?

Timestamp, level, request id, route and user id — enough context to find the failing request and reconstruct what happened.

7 · Interview ▾

How should an API communicate errors to clients?

Consistent JSON shape with a status code, a machine-readable code and a human message — same shape for every endpoint.

What is graceful degradation, with an example?

Designing a feature's failure mode in advance: when the AI backend is down, show a friendly fallback instead of crashing or hanging.
