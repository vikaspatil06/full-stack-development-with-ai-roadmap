Python OOP Deep — Dunder Methods, Dataclasses & Protocols

Classes that behave like built-ins

1. Dunder methods: the protocol behind the syntax

▶ YouTube reference — the video for this lesson

Python's operators are method calls in disguise. len(obj) calls __len__, obj == other calls __eq__, printing calls __repr__ or __str__, and for x in obj calls __iter__. Implementing these double-underscore methods makes your classes behave like built-in types everywhere — in f-strings, in sets, in sorted(). Two rules matter most: __repr__ should be an unambiguous developer representation (ideally valid Python that recreates the object), and defining __eq__ without __hash__ makes instances unhashable, which surprises everyone exactly once.

2. Dataclasses: kill the boilerplate

▶ YouTube reference — the video for this lesson

Most classes exist to hold data, and hand-writing __init__, __repr__ and __eq__ for each is pure boilerplate. The @dataclass decorator generates all three from annotated fields, with options like frozen=True for immutability (which also restores hashability) and field(default_factory=list) for mutable defaults — never use a bare list as a default, or every instance shares it. A dataclass is still a normal class: add methods freely, and reach for __post_init__ when fields need validation or derivation at construction.

3. Protocols: duck typing, checked

▶ YouTube reference — the video for this lesson

Python has always allowed duck typing: if it has the right methods, it fits, whatever its class. typing.Protocol makes that contract explicit and checkable: declare a protocol with the methods you need, and any class with those methods satisfies it — no inheritance required. A type checker then verifies callers only pass objects with the right shape. This is structural typing, and it is how you write flexible code (anything drawable, anything with a read method) without a tangle of abstract base classes.

4. Properties: attributes with a gatekeeper

▶ YouTube reference — the video for this lesson

A property looks like a plain attribute from outside but runs code on access: the getter computes or validates, the setter rejects bad values. The pattern is a private _xp field behind a public xp property that refuses negatives. Properties let you start with a plain attribute and add validation later without changing any calling code — the Pythonic answer to the getter/setter ceremony other languages force from day one. Use them when an invariant must hold; do not wrap every attribute by reflex.

from dataclasses import dataclass, field

@dataclass(frozen=True)
class Lesson:
    id: str
    title: str
    xp: int = 20
    tags: tuple = ()

class Progress:
    def __init__(self):
        self._xp = 0

    @property
    def xp(self):
        return self._xp

    @xp.setter
    def xp(self, value):
        if value < 0:
            raise ValueError("xp cannot be negative")
        self._xp = value

    def __repr__(self):
        return f"Progress(xp={self._xp})"

What happens when you define __eq__ but not __hash__?

Instances become unhashable, so they cannot be used in sets or as dict keys. Defining __eq__ sets __hash__ to None unless you also define it (or use a frozen dataclass).

Why must mutable dataclass defaults use default_factory?

A bare list default would be shared by every instance, so appending to one object's list would change them all. default_factory creates a fresh value per instance.

How does a Protocol differ from an abstract base class?

A protocol is structural: any class with the right methods satisfies it without inheriting anything. An ABC requires explicit subclassing. Protocols formalise duck typing.

When is a property worth adding over a plain attribute?

When an invariant must hold — validation, clamping, or a computed value — or when you need to add that logic later without changing callers.

Bonus round — flashcards (+5 XP each)

Define each term out loud before revealing. These count toward your score below.

What is “Dunder method”?

A double-underscore method like __len__ or __eq__ that Python calls for operators and built-ins, letting classes behave like built-in types.

What is “__repr__”?

The unambiguous developer representation of an object, ideally valid Python that recreates it.

What is “Dataclass”?

A class decorated with @dataclass that generates __init__, __repr__ and __eq__ from annotated fields.

What is “frozen dataclass”?

An immutable dataclass whose instances are hashable and cannot be modified after creation.

What is “Protocol”?

A structural interface from typing: any class with the declared methods satisfies it, with no inheritance required.

What is “Property”?

An attribute that runs getter and setter code on access, enforcing invariants behind plain attribute syntax.

7 · Interview ▾

Explain __repr__ versus __str__.

__repr__ is the unambiguous developer representation, ideally recreating the object; __str__ is the friendly user-facing text. If only one is defined, define __repr__ — Python falls back to it for str.

Why choose a dataclass over a hand-written class?

It generates __init__, __repr__ and __eq__ from the field declarations, removing boilerplate and its bugs, with options for immutability and ordering when needed.
