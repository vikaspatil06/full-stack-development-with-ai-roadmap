Git Workflows

Branches, merges, and commits that tell a story

Goal — by the end of this lessonBy the end you can work a feature-branch flow confidently, write commits a teammate can review, resolve a merge conflict calmly, and explain rebase vs merge honestly.

1. Git is a graph, not a folder backup

▶ YouTube reference — the video for this lesson

Every commit is a snapshot plus a pointer to its parent(s). A branch is just a movable label on a commit. That one model explains everything: merging joins two lines of history; a conflict means both lines changed the same lines of the same file and a human must decide.

2. The daily workflow

▶ YouTube reference — the video for this lesson

▸ Code example — see the Code section below.

Small commits with messages that say why ("make privacy flag per-user", not "fix stuff") are what let future-you — and reviewers — understand a change in seconds. This is also where your standing rule fits: batch changes locally, push only when you say "commit".

3. Merge vs rebase

▶ YouTube reference — the video for this lesson

Merge preserves true history with a merge commit — safe, shared-branch friendly. Rebase replays your commits onto the latest base for a linear story — cleaner, but it rewrites commits, so never rebase history others have pulled. Rule: rebase your own unpushed work; merge shared work.

Conflict protocolDon't panic-delete. Open the file, read both sides between the conflict markers, decide the correct combined result, delete the markers, run the tests, commit. A conflict is a question, not an error.

3 · Code

git checkout -b feature/passport-privacy
# ... work, in small pieces ...
git add -p                 # stage deliberately, hunk by hunk
git commit -m "Passport: make privacy flag per-user"
git push -u origin feature/passport-privacy   # → open a PR

4 · Practice

Your taskIn a scratch repo: create two branches that edit the same line of one file, merge them, and resolve the conflict by hand. Then write three commit messages for Skillzify-style changes (a feature, a fix, a rules change) that each explain why in one line.

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

Why never rebase a branch teammates have already pulled?

Rebase rewrites commit hashes; teammates' clones then disagree with the remote history, producing duplicated commits and painful recovery.

What makes a commit message professional?

It states what changed and why in one searchable line — 'Passport: make privacy flag per-user' — not 'fix' or 'updates'.

6 · Interview

Merge vs rebase — when each?

Merge for shared/public history (preserves context, safe). Rebase for tidying your own local, unpushed commits into a linear story before sharing.

Walk me through your team's branching flow.

Feature branches off main, small reviewed PRs, CI required green, squash or merge per team convention, delete branch after merge.
