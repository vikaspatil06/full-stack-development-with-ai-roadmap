Firestore Queries & Indexes

Where, order, paginate — and the index error that teaches you the rules

1. Queries are built from filters, order and limits

▶ YouTube reference — the video for this lesson

A Firestore query starts from a collection and chains conditions: where filters documents, orderBy sorts them, limit caps how many come back. Every clause you add narrows the result, and every document returned costs one read — so a query that fetches 200 documents to show 10 is a billing bug, not just a slow page. Skillzify's community page, for example, asks for questions ordered by creation time, limited to the first page, instead of pulling the whole collection and sorting in JavaScript.

2. The composite index rule

▶ YouTube reference — the video for this lesson

Firestore can answer a query only if an index exists for that exact combination of fields. Single-field indexes are automatic; the moment you combine a range filter on one field with an order on another, or filter on two fields, Firestore refuses and returns an error containing a direct link to create the missing composite index. That error is not a failure — it is the database telling you exactly what it needs. Create the index in the console, wait for it to build, and the same query works.

3. What queries cannot do

▶ YouTube reference — the video for this lesson

Firestore has no joins, no full-text search and no server-side aggregation. You cannot ask for documents where any of five fields matches a substring, and you cannot ask the server to count or sum. Those jobs belong to a different layer: denormalised fields you maintain on write, a search service, or a small aggregation document updated by a Cloud Function. Designing around these limits is the real skill — the query syntax itself takes an afternoon.

▸ Code example — see the Code section below.

Pagination uses a cursor: the last document of the page you just showed. Pass it to startAfter and Firestore returns the next slice. Never use offset for paging through large lists — it still reads and charges for every skipped document.

3 · Code

import { collection, query, where, orderBy, limit, startAfter, getDocs } from "firebase/firestore";

const q = query(
  collection(db, "questions"),
  where("section", "==", "beginner"),
  where("answered", "==", true),
  orderBy("createdAt", "desc"),
  limit(10)
);
// First page: getDocs(q). Next page: same query plus startAfter(lastDoc).

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

Why does Firestore refuse a query that combines a filter on one field with an order on another?

No index exists for that field combination. Single-field indexes are automatic, but compound combinations need a composite index, which the error message links you to create.

Why is startAfter better than offset for pagination?

startAfter resumes from a cursor document, while offset still reads and bills for every document it skips.

6 · Interview

A query needs a composite index — what does that tell you about how Firestore executes queries?

Firestore answers queries from pre-built indexes, not by scanning documents. A query without a matching index cannot run, which is why reads stay fast and predictable at scale.

How would you implement search across lesson titles in Firestore?

Firestore has no full-text search. Maintain a lowercase keyword array on write and query it with array-contains, or use a dedicated search service for real text search.
