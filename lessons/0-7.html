Forms & Validation — Trust Nothing the Browser Sends

Client convenience, server authority

Goal — by the end of this lessonBy the end you can build an accessible form with layered validation, explain why client checks are only a courtesy, and write the server-side validation Skillzify relies on.

1. Forms are a contract

▶ YouTube reference — the video for this lesson

A form promises the user what will happen and promises the server what shape the data arrives in. Every field needs a label, a name, the right type, and a clear error state. Skillzify's signup and login forms follow this exactly: email type for email, password type for passwords, and required on the fields that must be present.

2. Client-side validation is UX, not security

▶ YouTube reference — the video for this lesson

HTML attributes like required, minlength and pattern, plus JavaScript checks on submit, give instant feedback without a round trip. They catch honest mistakes early. But they run in the user's browser, which the user controls — anyone can disable them, edit the page, or send a request with curl. Treat client validation as a courtesy for real users.

▸ Code example — see the Code section below.

3. Server-side validation is the gate

▶ YouTube reference — the video for this lesson

The server re-checks everything: presence, type, length, format and range. It rejects with a 400 and a specific message, never a stack trace. It also enforces size limits on the body itself, so a megabyte of junk in one field cannot exhaust memory. Skillzify's AI routes do exactly this before any Gemini call is made.

4. Accessible errors

▶ YouTube reference — the video for this lesson

Errors must be visible, specific and announced. Put the message next to the field, link it with aria-describedby, move focus to the first invalid field, and never rely on colour alone. A form that fails silently for a keyboard or screen-reader user is a broken form, however pretty it looks.

3 · Code

// Server-side: the only validation that counts
app.post("/api/signup", (req, res) => {
  const email = String(req.body.email || "").trim();
  if (!email.includes("@") || email.length > 200) {
    return res.status(400).json({ error: "Valid email required" });
  }
  res.json({ ok: true });
});

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

Why must the server validate a field the browser already validated?

Browser validation can be bypassed entirely with curl or DevTools. The server is the only code you control, so it is the only trustworthy gate.

What should a server return when validation fails, and what must it never return?

A 400 with a specific, user-safe message per field. Never a stack trace or internal detail that leaks how the server works.

6 · Interview

Explain defence in depth for a form.

Layered checks: HTML attributes for instant UX, JavaScript for richer feedback, server validation as the authority, and size limits plus rate limits against abuse.

How do you make form errors accessible?

Message beside the field, linked with aria-describedby, focus moved to the first error, and meaning conveyed by text, not colour alone.
