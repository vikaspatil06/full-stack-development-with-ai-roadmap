1. ViewModel: state with a longer life than the screen

▶ YouTube reference — the video for this lesson

Rotate the phone and the Activity is recreated — composable state dies, but a ViewModel survives configuration changes. It owns the screen's data and logic (load progress, handle events), exposes state, and stays free of UI code — which is what makes the logic unit-testable. Think of it as the Android counterpart of keeping state logic out of React components.

3. Coroutines: async without callback pyramids

▶ YouTube reference — the video for this lesson

▸ Code example — see the Code section below.

A suspend function can pause without blocking a thread; launch runs it in a scope tied to a lifecycle (viewModelScope cancels automatically when the ViewModel dies). This is Kotlin's answer to the async problems from Lesson 1.2 — Firestore calls, network and database work all become sequential-looking code that doesn't freeze the UI.

The through-line of this whole courseSeparate state/logic from rendering (1.3), keep side effects at the edges (1.4, 5.x), let lifecycles own cleanup. Android just gives the same ideas platform names.

Why does state belong in a ViewModel instead of the composable?

ViewModels survive configuration changes (like rotation) that recreate the UI, and they keep logic testable and out of rendering code.

What does 'suspend' mean for a coroutine function?

It can pause at await points without blocking its thread, resuming when the async work completes — with cancellation tied to its scope.

7 · Interview ▾

How do you keep Android UI state across rotation?

Hold it in a ViewModel, which is retained across configuration changes; composables render the ViewModel's state.

Coroutines vs threads/callbacks — the pitch?

Structured concurrency: async code reads sequentially, runs on managed scopes, and cancels with lifecycles — avoiding callback nesting and leaked threads.
