Goal — by the end of this lessonBy the end you can write tests with the built-in node:test runner, exercise Express routes with Supertest, mock external calls, and generate and read a coverage report.

1. node:test: the runner you already have

▶ YouTube reference — the video for this lesson

Since Node 18, a test runner ships with Node itself: node --test discovers files matching the test patterns, runs them, and reports pass or fail with no dependencies to install. Tests are plain functions using test() and describe() from node:test, with assertions from node:assert/strict. For a small service this is often all you need — no framework weight, no version churn — and it runs identically in CI because it is part of the runtime you already deploy.

2. Supertest: HTTP calls without a network

▶ YouTube reference — the video for this lesson

Testing an Express route by starting a real server and curling it is slow and flaky. Supertest instead hands your app object a fake HTTP layer: you write request(app).post("/api/tutor").send({...}) and assert on the status and JSON body, all in-process. The app never binds a port, tests run in parallel safely, and a failure shows the exact response. The one structural requirement: export the app separately from the code that listens, so tests can import the app without starting a server — a refactor Skillzify's server would need before its first route test.

3. Mocking the outside world

▶ YouTube reference — the video for this lesson

A route that calls Gemini must not call the real Gemini in tests: it is slow, costs quota, and returns different text every time. Mock at the boundary — replace the API client with a stub that returns a fixed reply, and assert your route handles success, empty input and upstream failure. node:test includes mock.fn() for this. The discipline from unit testing applies unchanged: mock external services, never the code under test, and keep one clearly-labelled live smoke test separate if you need end-to-end confidence.

4. Coverage: finding the untested branches

▶ YouTube reference — the video for this lesson

Node's built-in coverage (node --experimental-test-coverage, or c8 for richer reports) shows which lines and branches your tests executed. Read it as a map of blind spots: the error branch of the rate limiter, the 400 path of a validator — the code most likely to break in production and least likely to be exercised by hand. As with any coverage tool, the number itself is not the goal; the goal is that every risky behaviour has a test that would fail if it broke.

4 · Code ▾

▶ Run works for JavaScript snippets below — it runs in a sandboxed worker with a 2-second timeout. Python, HTML and CSS snippets are read-only here.

import { test } from "node:test";
import assert from "node:assert/strict";
import request from "supertest";
import app from "../app.js";

test("POST /api/tutor rejects an empty question", async () => {
  const res = await request(app)
    .post("/api/tutor")
    .send({ question: "" });
  assert.equal(res.status, 400);
});

test("POST /api/tutor answers a valid question", async () => {
  const res = await request(app)
    .post("/api/tutor")
    .send({ question: "What is a closure?" });
  assert.equal(res.status, 200);
  assert.ok(res.body.reply.length > 0);
});

Why must the app be exported separately from listen for Supertest?

Supertest imports the app and drives it in-process without binding a port. If importing the file also starts a server, tests collide on ports and cannot run in parallel.

What does node:test give you that needs no installation?

A built-in runner with test(), describe() and mocking, discovered by node --test — part of the runtime since Node 18, so CI needs no extra dependencies.

Why mock the Gemini call in route tests?

The real call is slow, costs quota and returns varying text, making tests flaky. A stub returns a fixed reply so the test checks your route's behaviour deterministically.

How should a coverage report be read?

As a map of blind spots — untested error branches and edge cases — not as a score to maximise. The goal is tests that fail when risky behaviour breaks.

Bonus round — flashcards (+5 XP each)

Define each term out loud before revealing. These count toward your score below.

What is “node:test”?

Node's built-in test runner (since Node 18): test(), describe() and mocking with no dependencies, run via node --test.

What is “Supertest”?

A library that drives an Express app in-process with fake HTTP requests, asserting on status and body without a real server.

What is “App/listen split”?

Exporting the Express app separately from the listen call so tests can import it without binding a port.

What is “Stub”?

A fake implementation of an external dependency returning fixed results, used to keep tests deterministic.

What is “mock.fn()”?

node:test's built-in mock function for replacing dependencies and asserting how they were called.

What is “Coverage report”?

A listing of which lines and branches tests executed — used to find untested risky code, not as a target.

7 · Interview ▾

How do you test an Express API without starting a server?

Export the app separately from listen, then use Supertest to send in-process requests and assert on status and body. No ports, no network, parallel-safe.

node:test versus Jest or Vitest — how do you choose?

node:test is zero-dependency and part of the runtime, ideal for backend services. Jest and Vitest add richer matchers, snapshots and frontend tooling, worth it when the project needs them.
