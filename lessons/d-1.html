Goal — by the end of this lessonBy the end you can analyse any solution's time and space complexity, recognise the Big-O classes that matter in interviews, and estimate whether a solution fits the limits before coding it.

1. Big-O is about growth, not stopwatches

▶ YouTube reference — the video for this lesson

Big-O describes how a solution's cost grows as the input grows. An O(n) scan of 10 items and of 10 million items differs by a factor of a million; an O(n²) solution differs by a factor of a trillion. That is why interviewers care about complexity more than raw speed: hardware changes, growth does not. Always state the cost in terms of the input size n, and drop constants and lower-order terms, because at interview scale only the dominant term decides whether you pass.

2. The classes you must recognise instantly

▶ YouTube reference — the video for this lesson

Memorise the ladder: O(1) constant, O(log n) halving, O(n) single pass, O(n log n) good sorting, O(n²) nested loops, O(2ⁿ) brute-force subsets. A useful sense of scale: n = 10⁵ allows O(n log n) easily, O(n²) needs 10¹⁰ operations and will time out, and O(2ⁿ) dies around n = 25. When you see nested loops over the same array, think n²; when you see a problem halved each step, think log n; when you see every subset tried, think 2ⁿ.

3. Counting loops and recursion

▶ YouTube reference — the video for this lesson

Sequential loops add, nested loops multiply, and a loop that halves its range each time contributes log n. Recursion costs depth times work per level: a recursion tree of depth n with one call per level is O(n) time and O(n) stack space, while branching recursion like naive Fibonacci explodes to O(2ⁿ). Always count the hidden costs too: slicing a list copies it in O(n), sorting costs O(n log n), and a hash-map lookup is O(1) on average but O(n) in the worst case.

4. Space, trade-offs, and the interview habit

▶ YouTube reference — the video for this lesson

Time and space trade against each other constantly: a hash map buys O(1) lookups with O(n) extra memory, and sorting in place saves memory but costs O(n log n) time. In an interview, name the complexity of your brute force first, then say what you will trade to improve it. That sentence alone signals senior thinking. Before coding, check the constraints: if n ≤ 10³, O(n²) is fine; if n ≥ 10⁵, you need O(n log n) or better.

def binary_search(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1

# Halves the search space each step: O(log n) time, O(1) space.

Why is an O(n²) solution unacceptable when n = 10⁵?

It needs about 10¹⁰ operations, far beyond the roughly 10⁸ operations a typical 1–2 second limit allows. You need O(n log n) or better.

A loop runs n times and inside it you slice a list of length n. What is the total complexity?

O(n²): each slice copies n elements, so n iterations times O(n) work per iteration.

7 · Interview ▾

Explain Big-O to a non-technical person in 30 seconds.

It describes how the work grows as the input grows. Doubling the input doubles the work for a linear solution, but quadruples it for a quadratic one — so we pick solutions whose work grows slowly.

Your solution is O(n) time and O(n) space. The interviewer asks for O(1) space. What do you do?

Look for an in-place approach: sort the input, use two pointers, or reuse the input array for bookkeeping, and state what you give up — usually time, or mutating the input.
