AI Agents & Tool Use — Beyond Single Prompts

1. From single prompt to agent loop

▶ YouTube reference — the video for this lesson

A single prompt is one round trip: question in, answer out. An agent is a loop: the model plans a next step, acts by calling a tool, observes the result, and repeats until the goal is met or a limit stops it. That loop is what lets a model do multi-step work — search, read, compute, write — instead of only describing it. Skillzify's AI modes are single-shot by design: one question, one Gemini call, one reply. An agent version of its tutor could look up the learner's progress, fetch the relevant lesson, run their code, and then answer with all of that in hand.

2. Tools: giving the model hands

▶ YouTube reference — the video for this lesson

A tool is a function the model may request, described by a schema: a name, a plain-language description of when to use it, and typed parameters. The model never executes anything itself — it emits a structured request, your code validates and runs the function, and the result goes back into the conversation as an observation. Good tool design is narrow and boring: one clear job per tool, strict parameter types, and errors returned as readable text the model can react to, not stack traces.

3. Guardrails: the loop needs a fence

▶ YouTube reference — the video for this lesson

An agent that can act can also act wrongly, repeatedly. Guardrails bound the damage: a maximum number of steps and tokens per run, an allowlist of tools per task, human approval before irreversible actions like sending messages or spending money, and validation of every tool argument server-side — the model's output is untrusted input, exactly like a form submission. Sandboxing matters too: code execution happens in an isolated environment with no access to secrets, the same discipline Skillzify applies to running learner code.

4. Multi-step reliability: errors compound

▶ YouTube reference — the video for this lesson

Each step in a loop can fail, and failures compound: a 95 percent reliable step repeated 20 times succeeds only about a third of the time. Reliable agents are designed for this — small verifiable steps, checkpoints where state is saved, retries with the error fed back to the model, and a final verification step that checks the goal was actually met. Keep the loop observable: log every plan, tool call and observation, because when an agent goes wrong, the trace is the only way to see where. The honest summary: agents trade the predictability of one prompt for capability across many steps, and the engineering is all in the guardrails.

const tools = [{
  name: "get_progress",
  description: "Get a learner's XP and completed lessons by user id.",
  parameters: {
    type: "object",
    properties: { userId: { type: "string" } },
    required: ["userId"]
  }
}];

async function runAgent(goal, maxSteps = 8) {
  const history = [{ role: "user", content: goal }];
  for (let step = 0; step < maxSteps; step++) {
    const reply = await callModel(history, tools);
    if (!reply.toolCall) return reply.text;
    const result = await executeTool(reply.toolCall);
    history.push({ role: "tool", content: String(result) });
  }
  return "Stopped: step limit reached.";
}

What are the three phases of the agent loop?

Plan: the model decides the next step. Act: it requests a tool call, which your code executes. Observe: the result returns to the model, which plans again until the goal is met or a limit stops it.

Who actually executes a tool the model requests?

Your code does. The model only emits a structured request; your server validates the arguments, runs the function, and returns the result as an observation.

Why does reliability drop so fast in long agent loops?

Step failures compound multiplicatively: even at 95 percent per step, a 20-step run succeeds only about a third of the time. Small verifiable steps and retries are the countermeasure.

Name three guardrails every production agent needs.

A step and token budget per run, an allowlist of tools per task, and human approval before irreversible actions — plus server-side validation of every tool argument.

Bonus round — flashcards (+5 XP each)

Define each term out loud before revealing. These count toward your score below.

What is “Agent loop”?

The plan-act-observe cycle a model repeats — deciding a step, calling a tool, reading the result — until the goal is met or a limit stops it.

What is “Tool schema”?

The name, description and typed parameters describing a function the model may request; your code executes it.

What is “Observation”?

A tool's result fed back into the conversation for the model to plan its next step from.

What is “Guardrail”?

A bound on agent behaviour: step and token budgets, tool allowlists, approval gates and argument validation.

What is “Step limit”?

A hard cap on loop iterations per run, preventing runaway agents from looping or spending forever.

What is “Trace”?

The logged record of every plan, tool call and observation in a run — the primary debugging tool for agents.

7 · Interview ▾

Explain the difference between a chatbot and an agent.

A chatbot answers in one round trip. An agent loops — plan, call tools, observe results — to complete multi-step goals, which adds capability and demands guardrails, budgets and observability.

How do you make a multi-step agent reliable?

Keep steps small and verifiable, checkpoint state, feed errors back for retry, cap steps and tokens, verify the final goal explicitly, and log the full trace so failures are debuggable.
