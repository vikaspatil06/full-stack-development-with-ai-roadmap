Room Deep — Migrations, Relations & Offline-First Android

Local data that survives upgrades and no signal

Goal — by the end of this lessonBy the end you can model related tables with @Relation, write a Room migration that preserves user data, observe queries as Flow, and design an offline-first sync pattern.

1. Relations: modelling joined data without SQL strings

▶ YouTube reference — the video for this lesson

Room entities are tables; relations connect them. A learner has many progress rows, a lesson has many exercises — and @Relation lets Room fetch a parent with its children in one query, generating the join for you. You declare a data class pairing the parent entity with a list of children, annotate it with @Embedded and @Relation, and mark the DAO method @Transaction so both queries run atomically. Foreign keys with cascade deletes keep the data honest: delete a lesson and its progress rows go with it, enforced by the database rather than by hopeful code.

2. Migrations: upgrading without wiping the user

▶ YouTube reference — the video for this lesson

When your schema changes between app versions — a new column, a new table — Room refuses to open the old database unless you provide a migration: a Migration(1, 2) object whose migrate function runs the SQL that transforms version 1 into version 2, such as ALTER TABLE lessons ADD COLUMN difficulty TEXT. The alternative, destructive fallback, deletes the user's data on upgrade — acceptable in a prototype, unforgivable in production. Every schema change gets a migration, and every migration gets a test that opens a version-1 database and verifies the data survives. Skillzify's Android app stores lessons and progress locally, so its migrations are what stand between an update and a learner losing their streak.

3. Flow from Room: the UI that updates itself

▶ YouTube reference — the video for this lesson

A DAO method returning Flow<List<Lesson>> re-emits automatically whenever the underlying table changes. The UI collects the flow and re-renders; no manual refresh, no polling, no stale screens. Combined with a ViewModel exposing that flow as state, the data layer becomes reactive end to end: write progress once, and every screen observing it updates. This is the Android counterpart of the web's re-render problem — solved by the database pushing changes instead of the UI pulling them.

4. Offline-first: local truth, synced when possible

▶ YouTube reference — the video for this lesson

Offline-first design treats the local database as the single source of truth: the UI always reads from Room, writes go to Room immediately, and a sync layer reconciles with the server when connectivity returns. The pattern needs three decisions: how changes are queued (an outbox table of pending operations), how conflicts resolve (last-write-wins, or server-wins for shared data), and how deletions propagate (tombstones, not hard deletes, so other devices learn). For a learning app used on buses and in dead zones, offline-first is not an optimisation — it is the difference between an app that works and one that spins.

val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL(
            "ALTER TABLE lessons ADD COLUMN difficulty TEXT NOT NULL DEFAULT 'easy'"
        )
    }
}

@Dao
interface LessonDao {
    @Query("SELECT * FROM lessons ORDER BY id")
    fun observeLessons(): Flow<List<Lesson>>

    @Transaction
    @Query("SELECT * FROM lessons WHERE id = :id")
    suspend fun lessonWithProgress(id: String): LessonWithProgress?
}

What does @Relation do, and why does its DAO method need @Transaction?

@Relation fetches a parent entity together with its children, generating the join. @Transaction ensures the parent and child queries run atomically, so the pair is consistent.

What happens if you ship a schema change without a migration?

Room throws an IllegalStateException when opening the database — or, with destructive fallback, silently deletes all user data. Both are production failures.

How does returning Flow from a DAO change the UI's job?

Room re-emits the query result whenever the table changes, so the UI just collects and renders. No manual refresh or polling is needed.

What is an outbox table in offline-first sync?

A local table recording pending write operations made offline, which the sync layer drains to the server when connectivity returns.

Bonus round — flashcards (+5 XP each)

Define each term out loud before revealing. These count toward your score below.

What is “@Relation”?

A Room annotation fetching a parent entity with its children in one generated join query.

What is “Migration”?

A Migration(from, to) object with the SQL transforming one schema version into the next, preserving user data across upgrades.

What is “Destructive fallback”?

Room's option to delete and recreate the database on schema mismatch — fine for prototypes, data loss in production.

What is “Flow from Room”?

A DAO returning Flow re-emits results automatically when the table changes, making the UI reactive.

What is “Offline-first”?

Architecture where the local database is the source of truth and the server is reconciled later, so the app works without connectivity.

What is “Outbox pattern”?

Queueing offline writes in a local table for later sync, with tombstones propagating deletions.

7 · Interview ▾

Explain offline-first architecture in one minute.

The local database is the single source of truth: UI reads and writes locally, always works offline, and a sync layer reconciles with the server later using an outbox queue and a stated conflict policy.

How do you test a Room migration?

Create a database at the old version with representative rows, run the migration, then open it at the new version and assert the schema matches and the data survived intact.
