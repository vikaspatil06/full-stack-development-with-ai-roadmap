Compose State & Lists

State hoisting, recomposition, and lists that scroll at 60fps

1. State is a value plus a change notification

▶ YouTube reference — the video for this lesson

In Compose, state is created with remember and mutableStateOf: a value the UI reads, and a setter that triggers recomposition — the framework re-running the composables that read the value. remember keeps the value across recompositions; without it, the state resets every time the screen redraws. derivedStateOf computes a value from other state and only recomputes when its inputs change, which is how you keep expensive derivations — like a filtered lesson list — from running on every keystroke.

2. State hoisting: state lives above the composable that uses it

▶ YouTube reference — the video for this lesson

Hoisting means moving state up to the caller and passing the value and an on-change callback down. A LessonCard does not own whether it is done; the screen owns the list of done lessons and passes done plus onToggle down. The card becomes stateless and reusable, the screen becomes the single source of truth, and the same screen can drive the card from a ViewModel's StateFlow. When two composables need the same state, hoist it to their common ancestor — that rule resolves most Compose state confusion.

3. Lists: LazyColumn, keys, and recomposition scope

▶ YouTube reference — the video for this lesson

LazyColumn renders only visible items, which is why a 250-lesson list scrolls smoothly: off-screen rows do not exist yet. Give each item a stable key — the lesson ID — so Compose can track identity across reordering and filtering instead of confusing one row for another. Recomposition is smart but not magic: reading state in a small composable confines the redraw to that composable, while reading it at the top of a screen redraws everything below. Keep state reads as low in the tree as possible.

▸ Code example — see the Code section below.

The mental model in one line: the UI is a function of state, recomposition re-runs the function, and keys tell it which rows survived.

4 · Code ▾

▶ Run works for JavaScript snippets below — it runs in a sandboxed worker with a 2-second timeout. Python, HTML and CSS snippets are read-only here.

@Composable
fun LessonList(lessons: List<Lesson>, done: Set<String>, onToggle: (String) -> Unit) {
  LazyColumn {
    items(lessons, key = { it.id }) { lesson ->
      LessonRow(
        lesson = lesson,
        isDone = lesson.id in done, // state read low in the tree
        onToggle = { onToggle(lesson.id) }
      )
    }
  }
}
// State lives in the ViewModel; the list only receives values + callbacks.

What is state hoisting, and why does it make a composable reusable?

Moving state to the caller and passing value plus callback down. The composable becomes stateless, so any screen can drive it with its own state.

Why does LazyColumn need a stable key per item?

So Compose tracks each row's identity across filtering and reordering; without keys it can attach the wrong state to the wrong row.

7 · Interview ▾

What triggers recomposition, and how do you keep it cheap?

Reading a State value during composition schedules a re-run of the composables that read it. Keep reads low in the tree and use derivedStateOf for expensive derivations.

remember vs rememberSaveable — when does the difference matter?

remember survives recomposition only; rememberSaveable also survives configuration changes and process death, so it is the right choice for input text.
