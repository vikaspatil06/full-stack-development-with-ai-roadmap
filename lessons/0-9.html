a11y is a feature, not a favour

Goal — by the end of this lessonBy the end you can audit a page for the core accessibility failures, fix them with semantic HTML, ARIA and keyboard support, and explain why accessibility is also good engineering.

1. Who accessibility is for

▶ YouTube reference — the video for this lesson

Accessibility means the page works for people using screen readers, keyboards, voice control, magnification, or high-contrast settings — and for everyone on a cracked phone screen in bright sunlight. Around one in six people live with a disability, and interviewers increasingly ask about this because products that exclude users lose users.

2. Semantic HTML does most of the work

▶ YouTube reference — the video for this lesson

Real buttons, real links, real headings in order, labelled form fields and alt text on images give assistive technology the structure it needs for free. A div with an onclick is invisible to a keyboard user; a button works with Enter, Space, focus rings and screen readers with zero extra code. Skillzify's nav and forms use real elements for exactly this reason.

▸ Code example — see the Code section below.

3. ARIA fills the gaps

▶ YouTube reference — the video for this lesson

ARIA attributes describe what HTML cannot: aria-label names an icon-only button, aria-describedby links a hint to its field, aria-live announces dynamic changes like a toast, and roles describe custom widgets. Rule one of ARIA: do not use it when a native element already does the job. Rule two: a wrong ARIA attribute is worse than none.

4. Contrast, focus and testing

▶ YouTube reference — the video for this lesson

Text needs a contrast ratio of at least 4.5 to 1 against its background, and focus must always be visible — never remove the outline without replacing it. Test by tabbing through the whole page with the keyboard alone, then run a screen reader for five minutes. Automated checkers catch roughly a third of issues; the keyboard test catches the rest.

3 · Code

<!-- Accessible: real button, labelled, focusable -->
<button aria-label="Toggle dark mode">🌙</button>
<label for="email">Email</label>
<input id="email" type="email" aria-describedby="email-hint">
<p id="email-hint">We never share your email.</p>

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

Why is a real button better than a clickable div?

A button is focusable, works with Enter and Space, announces itself to screen readers, and shows a focus ring — a div does none of that without manual work.

When should you use ARIA, and when should you avoid it?

Use ARIA only when no native HTML element expresses the meaning; prefer native elements first, because a wrong ARIA attribute is worse than none.

6 · Interview

What is the first rule of ARIA?

Do not use ARIA if a native HTML element or attribute already provides the semantics — native elements are tested, free and reliable.

How do you test accessibility beyond automated tools?

Keyboard-only navigation through the whole page, a screen reader pass, and manual checks of contrast, focus visibility and heading order.
