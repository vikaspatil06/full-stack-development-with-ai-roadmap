Offline Persistence

Your app keeps working when the network does not

Goal — by the end of this lessonBy the end you can enable Firestore offline persistence, explain what happens to reads and writes while offline, and describe how pending writes sync and can conflict when the connection returns.

1. Turning the cache on

▶ YouTube reference — the video for this lesson

Firestore can keep a local copy of the data your app has already read, so the app keeps working with no network at all. On the web you enable it with persistent local cache backed by IndexedDB; on Android it is on by default. Once enabled, reads are served from the cache when the server is unreachable, and the app behaves as if the data is simply there. This is why a learner on a train can still open Skillzify lessons and see their progress — the data was cached on earlier visits.

2. Writes queue, they do not fail

▶ YouTube reference — the video for this lesson

When offline, a write does not throw an error. Firestore stores it in a local queue and applies it to the cached data immediately, so the UI updates as if the write succeeded. When the connection returns, the queued writes are sent to the server in order. Your code should treat a write as done locally and listen for the server confirmation separately, rather than assuming the network is always there.

3. Knowing what is cached and what is confirmed

▶ YouTube reference — the video for this lesson

Every snapshot carries metadata: whether it came from the cache and whether it has pending writes. Showing a small offline or syncing indicator from that metadata is the difference between an app that feels broken and one that feels honest. The hard edge is conflict: if two devices changed the same field while offline, the last write to reach the server wins at the field level, which is exactly why Skillzify merges per field with rules like union for lessons and max for XP instead of trusting last-write-wins for everything.

▸ Code example — see the Code section below.

The multiple-tab manager matters: without it, two tabs of the same site can fight over the IndexedDB cache. With it, tabs share one cache cleanly.

3 · Code

import { initializeFirestore, persistentLocalCache, persistentMultipleTabManager } from "firebase/firestore";

const db = initializeFirestore(app, {
  localCache: persistentLocalCache({
    tabManager: persistentMultipleTabManager()
  })
});

// In a snapshot listener, check the truth of what you see:
onSnapshot(docRef, (snap) => {
  const fromCache = snap.metadata.fromCache;
  const pending = snap.metadata.hasPendingWrites;
  render(snap.data(), { fromCache, pending });
});

5 · Check

Say your answer out loud first, then reveal. Mark “I knew it” for +5 XP each.

What happens to a Firestore write made while the device is offline?

It is queued locally, applied to the cache immediately so the UI updates, and sent to the server in order when the connection returns.

How can your UI tell cached data apart from server-confirmed data?

Snapshot metadata: fromCache says the data came from the local cache, and hasPendingWrites says local writes have not reached the server yet.

6 · Interview

Why is offline support a data-design decision, not just a toggle?

Because conflicts are resolved by your merge rules. Last-write-wins loses progress, so fields need per-field rules — union for sets, max for XP — chosen from what each field means.

When would you NOT enable offline persistence?

For data that must never be stale or stored on the device — shared admin dashboards, sensitive records — or where cache size and multi-tab behaviour add risk without benefit.
